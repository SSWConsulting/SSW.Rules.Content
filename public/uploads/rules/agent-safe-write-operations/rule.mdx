A connection drops after the server saves an order. The AI agent sees a timeout, assumes nothing happened and tries again. Northwind now has two orders ready to ship for one request.

When you build write tools for agents, make retries harmless and outcomes explicit. Give the agent a preview, limit its access and require trusted approval for changes that are hard to undo. These safeguards belong in the application, so they still work when an agent ignores an instruction or loses its context.

## Preview the change and limit its scope

Apply this contract to writes through a CLI, HTTP API or [MCP server](/mcp-server).

A dry run checks permissions and business validation, then returns the proposed targets, changes and side effects without applying them. For the Northwind reorder, show the customer, quantities, price and whether saving also queues shipment. Validate again when executing: prices, permissions and records can change after the preview. Use a version precondition when execution must match the preview exactly.

Scope the tool's credentials to the required actions and resources, and enforce the caller's authorisation on every call, including replays. A tool that creates orders does not need permission to delete customers. Follow [least privilege](/give-users-least-privileges); [Azure RBAC guidance](https://learn.microsoft.com/en-us/azure/role-based-access-control/best-practices) explains how roles and scopes limit access. A safe response format cannot compensate for excessive permissions.

## Return an outcome the agent can act on

Return the saved record's ID and the fields the caller is authorised to see. Use the authoritative write response or read the record back; do not echo the requested values as proof they were saved. For a delete, return a receipt identifying the deleted record instead.

Define explicit outcome states. These are an application contract, not standard MCP fields:

| Outcome | What the tool knows | What the agent does next |
| --- | --- | --- |
| `saved` | The write is confirmed and the returned data is verified | Use the returned ID and data |
| `saved-unverified` | The write is confirmed, but the follow-up read failed | Look up the known ID; do not create again |
| `unknown` | A timeout or connection loss leaves completion uncertain | Reconcile or retry under the documented idempotency contract |
| `pending` | Work is accepted but incomplete | Check the operation ID until it reaches a final outcome |
| `failed` | The operation is rejected or rolled back with no business side effects | Fix the reported cause before retrying |

An HTTP error alone does not prove the write failed. A bulk operation also returns per-item outcomes so the agent does not repeat successful items. For a CLI, print structured results with stable error codes; exit non-zero for failure or uncertainty and document how pending work is polled. Follow the guidance on [detailed error messages](/do-you-return-detailed-error-messages).

## Prevent duplicate effects on the server

An **idempotent operation** has no additional business effect when repeated with the same arguments. A warning saying "do not create again" cannot provide that guarantee. Implement duplicate prevention on the server:

* **One key per intent** - Create a unique, opaque idempotency key once and persist it before the first attempt. Reuse it for retries of that request; a deliberate new reorder gets a new key
* **Bind the key** - Scope it to the caller and operation, and reject the same key with a different payload
* **Handle concurrency and crashes** - Commit the database change and its key/result record atomically. Concurrent requests with the same key must not both perform the write
* **Document retention and recovery** - Return the stored result for a completed request. If the first request is still running, return pending or a documented retry response. Publish the retention window; after expiry, reconcile rather than assuming the key still protects the request
* **Cover downstream effects** - A local transaction cannot undo an external shipment request. Use downstream idempotency or reconciliation, and [the Transactional Outbox pattern](/use-transactional-outbox-pattern) for reliable event publication with consumers that tolerate duplicates

[Stripe's idempotent requests](https://docs.stripe.com/api/idempotent_requests) provide a concrete implementation example. Its API v1 stores responses after execution begins, rejects changed parameters and may prune keys after at least 24 hours. Those are Stripe's rules; document your tool's own contract. Bound retries with a deadline and backoff instead of looping indefinitely.

A domain uniqueness constraint can provide another defence, such as a unique customer purchase-order reference. Identical order lines alone are not a duplicate: a customer can intentionally reorder them.

An operation that already has idempotent business effects may not need a key. Setting a field to a fixed value still needs a version check when a retry could overwrite a later edit; HTTP's [If-Match precondition](https://www.rfc-editor.org/rfc/rfc9110.html#name-if-match) addresses this lost-update problem.

## Require trusted approval for high-impact changes

For destructive, sensitive or large bulk writes, show the exact targets, effects and recovery limits before a person approves. Enforce approval outside the agent's control. For example, a server can require a short-lived approval token issued through an authenticated human flow and bound to the caller, operation, payload and record versions. Reject an expired or mismatched approval. An agent-supplied `--yes` flag is only an acknowledgement.

The MCP [tool annotations](https://modelcontextprotocol.io/specification/2026-07-28/schema#toolannotations) `destructiveHint` and `idempotentHint` describe behaviour; they neither enforce approval nor prevent duplicates. Treat annotations from untrusted servers as untrusted.

Keep routine, reversible writes within an agreed scope so approval prompts remain meaningful. For broader agent permissions and human supervision, see [how to keep cloud agents secure](/cloud-ai-agents#how-do-you-keep-a-cloud-agent-secure).

## Keep a receipt and a recovery path

Record who authorised the operation, the agent/run reference, target IDs, time, outcome and correlation ID in an access-controlled audit trail. Retain the minimum change details needed to investigate and recover; exclude credentials and unnecessary personal data.

Expose the permitted reversal and its limits. Northwind can cancel an unshipped order, but cannot unsend a shipment; it needs a returns process instead. Treat cancellation as another authorised, auditable write with safe retries. [Compensating transactions](https://learn.microsoft.com/en-us/azure/architecture/patterns/compensating-transaction) may fail and do not necessarily restore the original state, so provide an escalation path when automatic recovery cannot finish.

Before exposing the tool, exercise the failure path in a disposable fixture:

1. Commit an order, then drop the response. Retry with the same key and payload. Confirm one order and one intended shipment effect
2. Send concurrent same-key requests, then reuse that key with changed quantities. Confirm a single write and rejection of the changed payload
3. Check that dry runs change no business data, stale versions and invalid approvals are rejected, and denied callers cannot obtain a replayed receipt
4. Cancel the test order through the recovery path. Confirm its final state and a linked audit record
