The ideal development workflow is to clone the repository, make changes in Power BI Desktop, and follow the standard feature-branch and pull-request process.

However, when an administrator needs to make a small Power BI report change without waiting for a developer, a Git-connected Development workspace provides a simple editing experience.

## What is a Power BI workspace?

A Power BI workspace is a shared location where users can view, edit, and manage reports, semantic models, and other Power BI items. Use the workspaces as follows:

* **Development** – used by administrators to edit and test reports on a feature branch
* **Staging** – connected to main and used to validate approved changes
* **Production** – contains approved reports used by end users and is updated only through the deployment pipeline

## How does a workspace work with Git?

A workspace connects to one Git repository, one branch, and one repository folder at a time. Changes made in the workspace are compared with its connected branch.

## How to commit changes from workspace

1\. Open the Development workspace.

2\. Open **Source control** | **Branches** | **Switch branch** | **New Branch**, and create a feature branch from the latest main branch. The workspace switches to the new branch.

<imageEmbed alt="Source control pane with Switch branch highlighted" size="medium" showBorder={false} figurePrefix="none" figure="Source control | Branches | Switch branch" src="/uploads/rules/power-bi-safe-changes/source-control-switch-branch.png" />

<imageEmbed alt="Switch branch dialog with New Branch highlighted" size="medium" showBorder={false} figurePrefix="none" figure="Switch branch | New Branch" src="/uploads/rules/power-bi-safe-changes/switch-branch-new-branch.png" />

3\. Edit, save, and test the report.

4\. Open **Source control** and review the changed items on the **Changes** tab.

<imageEmbed alt="Changes – workspace edits that have not been committed to Git" size="large" showBorder={false} figurePrefix="none" figure="Changes ① - workspace edits that have not been committed to Git" src="/uploads/rules/power-bi-safe-changes/power-bi-changes.png" />

5\. Enter a clear commit message and commit the changes.

6\. Create a PR from the branch and ask for review.

<imageEmbed alt="Git history for Power BI report" size="medium" showBorder={false} figurePrefix="none" figure="Git history for Power BI report" src="/uploads/rules/power-bi-safe-changes/azure-devops-powerbi-git.png" />

## How are Power BI changes deployed?

<imageEmbed alt="Power BI deployment strategy" size="large" showBorder={false} figurePrefix="none" figure="Power BI deployment strategy" src="/uploads/rules/power-bi-safe-changes/powerbi-deployment-strategy.png" />

1\. Review and merge the approved pull request into main.

2\. Sync the Staging workspace with the latest changes from main.

3\. Test the updated reports in Staging.

4\. Open the Power BI deployment pipeline.

<imageEmbed alt="Power BI deployment pipeline" size="medium" showBorder={false} figurePrefix="none" figure="Power BI deployment pipeline example" src="/uploads/rules/power-bi-safe-changes/powerbi-deployment-pipeline.png" />

5\. Compare the Staging and Production workspaces.

6\. Deploy the approved changes to Production.

Your changes are now live 🎉
