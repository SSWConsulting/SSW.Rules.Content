When someone runs `git blame` on a strange line of code months later, they ask "why is this here?". If the branch, commits, and pull request point back to a PBI, the answer is one click away: the requirement, the discussion, the acceptance criteria, and the Done video. If they don't, the context is lost.

**Every branch, commit, and PR should be traceable to a PBI.**

<endIntro />

## What to link

Git is distributed. A branch can be created in the GitHub UI, on the command line, by an IDE, or by an AI agent, so you can't rely on a tool to make the link for you. Put the PBI number where it travels with the code:

1. **Branch name** - Follow a [branch naming convention](/branch-naming) that includes the PBI number
2. **Commit messages** - Reference the PBI in every commit
3. **Pull request** - Reference the PBI in the [PR description](/write-a-good-pull-request)

The first 2 are the most important, because they work no matter where the branch was created. Opening a draft PR straight away and linking it to the PBI also gives visibility, but it's a weaker substitute for a good branch name and good commit messages.

## Using GitHub

### Create the branch from the issue

The easiest way to link a branch to an issue is to create it from the issue itself. In the issue sidebar, under **Development**, click **Create a branch**. GitHub suggests a name starting with the issue number (e.g. `1234-login-fails-for-sso-users`). Edit it to add a category prefix (e.g. `bugfix/1234-login-fails-for-sso-users`) so it follows your [naming convention](/branch-naming). The branch appears in the issue's **Development** section so anyone looking at the issue can see the work in progress.

From the command line, the [GitHub CLI](https://cli.github.com/manual/gh_issue_develop) does the same thing:

```bash
gh issue develop 1234 --name bugfix/1234-login-fails-for-sso-users --checkout
```

See [Creating a branch to work on an issue](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/creating-a-branch-for-an-issue) for details.

<boxEmbed
  style="info"
  body={<>
    **Note:** Only branches created from the issue (or with `gh issue develop`) appear in the **Development** section. A branch created anywhere else isn't linked, which is why the branch name and commit messages still matter.
  </>}
  figurePrefix="none"
  figure=""
/>

### Reference the issue in commits and PRs

When a commit message or PR description contains `#1234`, GitHub [autolinks it](https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/autolinked-references-and-urls) and adds a reference to the issue's timeline. The issue then shows every commit and PR that touched it.

Avoid closing keywords such as `Closes #1234` or `Fixes #1234`. They close the issue as soon as the PR is merged (or the commit reaches the default branch), before the work is tested, deployed, and [closed with context](/close-pbis-with-context). Use a neutral phrase like `Relates to #1234` instead. If your team links PRs from the **Development** sidebar, also turn off **Auto-close issues with merged linked pull requests** in the repository settings, as described in [Do you avoid linking issues to PRs in GitHub?](/avoid-auto-closing-issues).

### Enforce it

On plans that support them, [ruleset metadata restrictions](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets#metadata-restrictions) can require branch names and commit messages to match a pattern, such as one containing a PBI number.

If you create branches through Azure DevOps, you can link them to a work item during the creation process.

<imageEmbed
  alt="Azure DevOps Create a branch dialog with a work item selected"
  size="large"
  showBorder={false}
  figurePrefix="good"
  figure="Linking the PBI when creating the branch"

In Azure Repos, a commit message containing `#1234` links the commit to work item 1234. If your code is in GitHub and your backlog is in Azure Boards, use `AB#1234` instead, as described in [Link GitHub commits and pull requests to work items](https://learn.microsoft.com/en-us/azure/devops/boards/github/link-to-from-github?WT.mc_id=DOP-MVP-33518).

Learn more in [Linking Work Items to Git Branches, Commits, and Pull Requests](https://devblogs.microsoft.com/devops/linking-work-items-to-git-branches-commits-and-pull-requests?WT.mc_id=DOP-MVP-33518).

### Enforce it

You can [set up Branch Policies](https://learn.microsoft.com/en-us/azure/devops/repos/git/branch-policies?WT.mc_id=DOP-MVP-33518) on your main branches to require linked work items on every pull request.
