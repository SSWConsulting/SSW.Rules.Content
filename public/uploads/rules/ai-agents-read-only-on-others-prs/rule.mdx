You ask an AI agent to review a teammate's pull request. It finds a merge conflict, merges `main`, fixes it and pushes. The agent runs with your credentials, so the push is yours. On a protected branch, your approval can be dismissed and the PR waits for another reviewer. The author finds commits on their branch that they didn't write.

**Read-only means the agent never changes the branch: it reads, comments when asked, and approves only when told.** Don't leave this to each developer's habits. Make it part of your team's base AI agent setup, so every agent in every repository starts from it.

<endIntro />

## What may the agent do?

| Action | On someone else's PR |
| --- | --- |
| Read the diff, checks and comments | ✅ Yes |
| Post findings | ✅ When asked, as comments or suggested changes |
| Report conflicts and failing checks | ✅ In the findings |
| Approve | ⚠️ Only when told, for this PR, and only if you're the expected reviewer |
| Commit, push, merge `main`, rebase or resolve conflicts | ❌ Only after the author hands it over |
| Merge the PR | ❌ Never |

The expected reviewer is whoever the team relies on for this PR, such as the assigned reviewer or a required code owner. If that's someone else, leave approval to them.

## Why does a push from your account matter?

The figure shows a branch with two GitHub settings on, both available in [branch protection](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches#require-pull-request-reviews-before-merging) and [rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets#require-a-pull-request-before-merging). In the order they bite:

* **Dismiss stale pull request approvals when new commits are pushed** - Jordan's merge of `main` changes the diff, so GitHub dismisses Jordan's approval
* **Require approval of the most recent reviewable push** - Jordan is now the last pusher, so Jordan's re-approval doesn't count. Someone else must approve. Because the merge brought in new changes from `main` after the review was submitted, this setting also dismisses the approval on its own

## How do you put it in your base setup?

Add this to your global instructions file. See [Do you keep universal rules for your AI agent in a global instructions file?](/global-rules-for-ai-agents)

```markdown
* When reviewing a PR the user didn't author, read it and draft findings.
  Post comments or suggested changes only when the user asks.
* Never commit, push, merge the base branch in, rebase or resolve conflicts
  on a PR the user didn't author, unless the user tells you to because the
  author handed it over. Report conflicts and failing checks for the author
  to fix. Never merge the PR.
* Approve only when the user tells you to for this PR and is the expected
  reviewer. Don't dismiss other people's reviews or change assignees or reviewers.
* Apply these instructions to every subagent you delegate to.
```

Your personal global file covers you. If the team relies on this default, put it in each repository's [AGENTS.md](/write-agents-md) or [share it centrally](/centralize-ai-workflows).

## How do you enforce it?

Instructions aren't enforcement. Command rules can't tell whose branch a push goes to, so make `git push` ask. The rule matches command text, so a variant such as `git -C . push` gets past it. See [Do you commit a shared settings file for your AI coding agents?](/shared-ai-agent-settings) for the equivalent in each tool.

`.claude/settings.json` (committed)

```json
{
  "permissions": {
    "ask": ["Bash(git push *)"]
  }
}
```

These are guardrails, not security; enforce review on the server with branch protection. See [Do you use branch protection?](/use-branch-protection)

## When doesn't this apply?

If Sam hands the PR over to Jordan or asks Jordan to push a specific fix, that changes the task from review to implementation. State the handover on the PR and authorize the agent's work for that PR. Approval requirements still apply, so another reviewer may need to approve afterward.

For small human edits during review, see [Do you know when to add your changes to an existing PR?](/adding-changes-to-pull-requests).
