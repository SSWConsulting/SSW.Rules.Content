You ask an AI agent to review a teammate's pull request (PR). It finds a merge conflict, merges `main`, resolves the conflict and pushes. If the agent uses your credentials, the push is yours. Branch protection can dismiss your approval and block the PR until another reviewer approves. Your teammate now has commits on their branch that they didn't write.

**A read-only review leaves the PR branch untouched: the agent drafts findings, posts them only when asked, and approves only when explicitly told.** Make this part of your team's base AI agent setup, so every agent follows the same default.

<endIntro />

## Set the review boundary

| Action | On someone else's PR |
| --- | --- |
| Read the diff, checks and comments; draft findings | Allowed |
| Post comments or suggested changes | Only when explicitly asked; leave applying suggestions to the author |
| Report conflicts and failing checks | Include them in the findings for the author to resolve |
| Approve | Only when explicitly asked for this PR, after reviewing it, and when you are the expected reviewer |
| Commit, push, update the branch, rebase or resolve conflicts | Only after an explicit handover and authorisation for the specific work |
| Merge the PR, dismiss reviews or change reviewers | Outside a review task |

The expected reviewer is whoever the team relies on to review this PR, such as the assigned reviewer or a required code owner. If that's someone else, leave approval to them. A request to "review" does not authorise posting, approving or fixing the branch.

## Understand the approval cost of a push

GitHub offers two separate review settings in [branch protection](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches#require-pull-request-reviews-before-merging) and [rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets#require-a-pull-request-before-merging):

* **Dismiss stale pull request approvals when new commits are pushed** dismisses approvals when a push changes the PR diff
* **Require approval of the most recent reviewable push** requires an authorised reviewer other than the last pusher to approve the latest changes; it does not generally dismiss all earlier reviews

With either setting, GitHub also dismisses approvals if the merge base introduces new changes after review. The merge base is the last common ancestor of the PR branch and its base branch.

The illustration assumes both settings apply, no bypass is used, and merging `main` changes the diff and merge base. Jordan's push dismisses the earlier approval; Jordan cannot satisfy the latest-push requirement. Another authorised reviewer must approve even if checks pass. In the read-only path, the conflict remains Sam's task; the review does not make the PR ready to merge.

## Make it the default

Add this to your [global instructions file](/global-rules-for-ai-agents):

```markdown
* When reviewing a PR the user did not author, read it and draft findings.
  Post comments or suggested changes only when explicitly asked.
* Leave the PR branch untouched. Do not commit, push, update the branch,
  rebase, resolve conflicts or apply suggestions. Report conflicts and
  failing checks for the author to fix.
* Change the branch only after the author hands over specific work and
  the user explicitly authorises that implementation task.
* Approve only when explicitly asked for this PR, after reviewing it,
  and when the user is the expected reviewer. A review task does not
  authorise merging, dismissing reviews or changing reviewers.
* Apply the same boundaries to every delegated agent.
```

Your personal global file covers you. To make this the team's default, put it in each repository's [AGENTS.md](/write-agents-md) or [share it centrally](/centralize-ai-workflows).

## Add guardrails and check the outcome

Instructions guide behaviour; permissions constrain the available actions. Use a read-only session and remove write-capable PR tools where possible. For Codex, select a read-only sandbox using its [permission controls](https://learn.chatgpt.com/docs/agent-approvals-security). Check connected tools separately: a local filesystem restriction is not a repository access policy.

For Claude Code, this `.claude/settings.json` fragment asks before matching Bash pushes in Manual mode. Permission-bypass mode skips those prompts. See the [permission documentation](https://code.claude.com/docs/en/permissions#bash-rule-limits):

```json
{
  "permissions": {
    "ask": ["Bash(git push *)"]
  }
}
```

The pattern does not identify the PR author or cover every way to push, such as `git -C . push` or a connected tool. Do not treat it as complete enforcement. Use [branch protection](/use-branch-protection) to enforce merge requirements on the server; protecting `main` does not prevent someone with access from pushing to a PR's source branch.

Before the review, record the PR's head commit. Afterwards, check that the agent added no commits, comments or review decisions beyond what you authorised. If the head changed, inspect who pushed; the author may have updated it while you reviewed. Test the default on a disposable PR with **example data** before relying on it.

## Make handovers explicit

If Sam asks Jordan to push a specific fix, the task changes from review to implementation. Record the scope of the handover on the PR and explicitly authorise the agent's work. Approval requirements still apply, so another reviewer may need to approve afterwards.

For small human edits during review, see [Do you know when to add your changes to an existing PR?](/adding-changes-to-pull-requests). That guidance does not give an agent standing permission to edit someone else's branch.
