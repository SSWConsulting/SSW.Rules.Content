You ask an AI agent to review a teammate's pull request. It finds a merge conflict, merges `main`, resolves the conflict and pushes. The agent uses your credentials, so the push is yours. Branch protection can dismiss your approval and block the PR until another reviewer approves. Your teammate now has commits on their branch that they didn't write.

**A read-only review leaves the branch untouched: the agent reads, comments when asked, and approves only when explicitly told.** Make this part of your team's base AI agent setup, so every agent in every repository follows the same default.

<endIntro />

## What may the agent do?

| Action | On someone else's PR |
| --- | --- |
| Read the diff, checks and comments | ✅ Yes |
| Post findings | ✅ When asked, as comments or suggested changes |
| Report conflicts and failing checks | ✅ In the findings |
| Approve | ⚠️ Only when told, for this PR, and only if you're the expected reviewer |
| Commit, push, merge `main`, rebase or resolve conflicts | ❌ Only after the author hands it over |
| Merge the PR | ❌ Never |

The expected reviewer is whoever the team relies on to review this PR, such as the assigned reviewer or a required code owner. If that's someone else, leave approval to them.

## Why does your push matter?

The figure shows a branch with two GitHub settings enabled, both available in [branch protection](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches#require-pull-request-reviews-before-merging) and [rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets#require-a-pull-request-before-merging). Here's how they affect the PR:

* **Dismiss stale pull request approvals when new commits are pushed** - Jordan's merge of `main` changes the diff, so GitHub dismisses Jordan's approval
* **Require approval of the most recent reviewable push** - Jordan is now the last pusher, so Jordan's re-approval doesn't count. Someone else must approve. Because the merge brought in new changes from `main` after the review was submitted, this setting also dismisses the approval on its own

## Make it the default

Add this to your global instructions file. See [Do you keep universal rules for your AI agent in a global instructions file?](/global-rules-for-ai-agents)

```markdown
* When reviewing a PR the user didn't author, read it and draft findings.
  Post comments or suggested changes only when the user asks.
* Never commit, push, merge the base branch into the PR branch, rebase or resolve
  conflicts on a PR the user didn't author, unless the user explicitly asks
  you to after the author has handed it over. Report conflicts and failing
  checks for the author to fix. Never merge the PR.
* Approve only when the user explicitly asks you to approve this PR and is
  the expected reviewer. Don't dismiss other people's reviews or change
  assignees or reviewers.
* Apply these instructions to every subagent you delegate to.
```

Your personal global file covers you. To make this the team's default, put it in each repository's [AGENTS.md](/write-agents-md) or [share it centrally](/centralize-ai-workflows).

## Add guardrails

Instructions aren't enforcement. Command rules can't tell whose branch a push targets, so require approval for `git push`. The rule below matches command text, so a variant such as `git -C . push` bypasses it. See [Do you commit a shared settings file for your AI coding agents?](/shared-ai-agent-settings) for the equivalent in each tool.

`.claude/settings.json` (committed)

```json
{
  "permissions": {
    "ask": ["Bash(git push *)"]
  }
}
```

These are guardrails, not security; enforce review on the server with branch protection. See [Do you use branch protection?](/use-branch-protection)

## When doesn't this apply?

If Sam hands the PR over to Jordan or asks Jordan to push a specific fix, the task changes from review to implementation. State the handover on the PR and authorise the agent's work for that PR. Approval requirements still apply, so another reviewer may need to approve afterwards.

For small human edits during review, see [Do you know when to add your changes to an existing PR?](/adding-changes-to-pull-requests).
