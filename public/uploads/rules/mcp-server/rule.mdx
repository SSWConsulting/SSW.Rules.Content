Custom integrations for each AI assistant create more code to maintain. Copying business logic into those integrations also lets calculations and permission checks drift from the rest of your app.

Expose useful operations through an MCP (Model Context Protocol) server, with a thin adapter that calls your existing application core.

<endIntro />

## Why use an MCP server?

Think of MCP as a "USB port" for AI applications: a common protocol through which compatible clients can discover and call your app's tools. You implement the server interface once rather than build a separate connector for every client. Client capabilities and configuration still vary.

* **Without MCP** - Separate client-specific connectors multiply the integrations you maintain.
* **With MCP** - Compatible clients share one tool interface, while your application controls the operations it exposes.

MCP standardizes the connection. Your implementation still needs authentication, authorization and safe handling of tool calls. It does not automatically update deployed integrations or make them secure.

## Keep business logic behind a thin MCP adapter

Implement and test an operation in a shared application service or existing API before exposing it as an MCP tool. Keep business calculations, input constraints and resource permission checks in that core. Add a CLI when people or CI also need the operation. A tested library is enough when nobody needs a terminal command.

The MCP adapter only translates between the protocol and that core:

* Describe the tool and validate protocol inputs
* Obtain the caller from trusted authentication context, never from model-supplied roles or caller arguments
* Invoke the core, which still checks access to the requested resource
* Map domain results into safe tool responses

Follow the [MCP tools specification](https://modelcontextprotocol.io/specification/latest/server/tools) for protocol behaviour.

### Example: one stock rule, two entry points

A Northwind warehouse item has 20 units on hand, 8 reserved and 4 quarantined, so **8 are available**. Both a CLI command and an MCP tool report that number.

```csharp
// Each adapter copies the stock rule, and the copies drift.
int CliAvailable(Stock stock) => stock.OnHand - stock.Reserved;                     // 12 - forgot quarantine
int McpAvailable(Stock stock) => stock.OnHand - stock.Reserved - stock.Quarantined; // 8
```

**❌ Figure: Bad example - Each adapter has its own calculation, so the CLI reports 12 available while MCP reports 8**

```csharp
// Both adapters only delegate to the shared core.
int CliAvailable(Caller caller, string itemId) => inventory.GetAvailable(caller, itemId); // 8
int McpAvailable(Caller caller, string itemId) => inventory.GetAvailable(caller, itemId); // 8

// InventoryService - the one place the rule and the access check live.
public int GetAvailable(Caller caller, string itemId)
{
    var stock = stockStore.GetForCaller(caller, itemId); // denies warehouses the caller can't access
    return stock.OnHand - stock.Reserved - stock.Quarantined; // 20 - 8 - 4 = 8
}
```

**✅ Figure: Good example - Both adapters call InventoryService, so a stock rule change is made and tested once**

### Test and release both entry points

* Run the same scenarios through the CLI and MCP with the same caller and stock snapshot: unknown item, zero stock and denied warehouse access
* Keep domain regression tests on the shared core, and add adapter tests for tool schemas, error mapping and CLI exit codes
* Release each interface with the updated core - sharing source does not update binaries that are already deployed
