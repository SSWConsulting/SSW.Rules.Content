Custom integrations for each AI assistant create more code to maintain. Copying business logic into those integrations also lets calculations and permission checks drift from the rest of your app.

Expose useful operations through an MCP (Model Context Protocol) server, with a thin adapter that calls your existing application core.

<endIntro />

## Why use an MCP server?

Think of MCP as a "USB port" for AI applications: a common protocol through which compatible clients can discover and call your app's tools. You implement the server interface once rather than build a separate connector for every client. Client capabilities and configuration still vary.

* **Without MCP** - Separate client-specific connectors multiply the integrations you maintain.
* **With MCP** - Compatible clients share one tool interface, while your application controls the operations it exposes.

MCP standardizes the connection; your implementation still needs authentication, authorization and safe handling of tool calls. It does not automatically update deployed integrations or make them secure.

## Keep business logic behind a thin MCP adapter

Implement and test an operation in a shared application service or existing API before exposing it as an MCP tool. Keep business calculations, input constraints and resource permission checks in that core. Add a CLI when people or CI also need the operation; a tested library is enough when nobody needs a terminal command.

The MCP adapter describes the tool, validates protocol inputs, obtains the authenticated caller, invokes the core and maps domain results into safe tool responses. Obtain identity from trusted authentication context, never model-supplied roles or caller arguments. The core still checks access to the requested resource. Follow the [MCP tools specification](https://modelcontextprotocol.io/specification/latest/server/tools) for protocol behaviour.

For example, synthetic Northwind stock has 20 units on hand, 8 reserved and 4 quarantined: 8 are available. A CLI and MCP handler with separate calculations can disagree if one forgets quarantine. Calling the same inventory service makes that rule one implementation to maintain.

When exposing both CLI and MCP entry points, test them with the same caller and stock snapshot, including unknown items, zero stock and denied warehouse access. Share domain regression tests and add adapter checks for schemas, error mapping and CLI exit status. Release each interface with the updated core; sharing source does not update already deployed binaries.
