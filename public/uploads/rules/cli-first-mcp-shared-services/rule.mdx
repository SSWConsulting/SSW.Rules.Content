An internal service gains an MCP tool, so its business rules go straight into the tool handler. Later, an operator needs the same action from a terminal and CI needs it in a script. Copying the handler creates another implementation to fix, secure and test.

Build and test the service's operations in a CLI or shared library first. Put the MCP server on top as a **thin adapter**: it translates tool calls into those existing operations. Humans, scripts, CI and agents then use the same business rules and permission checks.

<endIntro />

## Build the operation before the MCP tool

[Exposing your app through an MCP server](/mcp-server) makes its operations available to agents. [Choosing CLI or MCP as an agent interface](/design-for-agent-experience) decides how agents call them. Both interfaces should call the same implementation.

1. **Define a useful operation** - For example, get available stock for a SKU in a warehouse. Give it explicit inputs, a result and predictable failures
2. **Implement and test the core** - Keep business calculations, input constraints and resource permission checks in one application service. It must run without an MCP host
3. **Exercise it through a CLI if people or CI need a command** - Provide a non-interactive command with help, structured output and a nonzero exit code on failure
4. **Add the MCP adapter** - Describe the tool and its input schema, obtain the authenticated caller, invoke the core and map its result or error into MCP

If an existing API already owns the operation, have both interfaces call that API. If nobody needs a terminal command, a tested shared library is enough; an otherwise unused CLI adds maintenance. A shared library can run inside the MCP process without another network hop or subprocess.

This applies [separation of business logic from presentation](/keep-business-logic-out-of-the-presentation-layer) to agent integrations. Microsoft's [application architecture guidance](https://learn.microsoft.com/en-us/dotnet/architecture/modern-web-apps-azure/common-web-application-architectures) explains how an independent application core makes logic reusable and easier to test.

## Keep Northwind's stock calculation in one place

**Illustration · example data:** Northwind's main warehouse holds 20 units of `NW-TEA`, with 8 reserved and 4 quarantined. Available stock is 8. Both requests below use the same authorised caller and stock snapshot.

The CLI includes the quarantine rule, but the calculation written directly in the MCP handler omits it. The agent sees 12 available while the operator sees 8.

The central C# operation can look like this. `IStockStore.Get` loads the requested stock row or reports an unknown SKU. `IInventoryAccess.RequireRead` rejects unauthenticated callers and callers without read access to that warehouse, before any stock lookup. `StockAvailability` contains the SKU and available quantity.

```csharp
using System.Security.Claims;

// In Northwind.Inventory; no MCP dependency
public sealed class InventoryService(
    IStockStore stock, IInventoryAccess access)
{
    public StockAvailability GetAvailable(
        ClaimsPrincipal caller, string warehouse, string sku)
    {
        ArgumentException.ThrowIfNullOrWhiteSpace(warehouse);
        ArgumentException.ThrowIfNullOrWhiteSpace(sku);
        access.RequireRead(caller, warehouse);
        var row = stock.Get(warehouse, sku);
        var available = Math.Max(0,
            row.OnHand - row.Reserved - row.Quarantined);
        return new StockAvailability(sku, available);
    }
}
```

**Figure: The shared operation enforces warehouse access and calculates available stock once**

The adapters obtain the caller from their trusted authentication context and pass it to this operation. The caller's identity, roles and warehouse permissions must never come from model-supplied tool arguments or CLI flags.

## Keep protocol responsibilities in the wrapper

MCP standardises tool discovery, schemas and invocation; it does not require a CLI underneath. The CLI-first sequence is an architecture recommendation. Follow the [MCP tools specification](https://modelcontextprotocol.io/specification/latest/server/tools) for protocol behaviour and your SDK's documentation for registration and result mapping.

The wrapper still validates tool inputs, authenticates requests and formats responses. Translate expected domain failures into safe, useful tool errors, using `isError: true` for tool execution failures. Keep business decisions in the core. Share the domain tests, then add adapter tests for CLI exit codes and JSON output, and MCP schemas and error mapping.

Shared permission checks do not give every caller the same privileges. Preserve each caller's identity and permitted warehouse access. For a protected HTTP server, use the [MCP HTTP authorisation flow](https://modelcontextprotocol.io/specification/latest/basic/authorization); local stdio servers obtain credentials from their environment instead. Neither transport replaces the core's resource permission checks.

## Check that both interfaces agree

* Run `northwind inventory available --warehouse main --sku NW-TEA --json` without an MCP host; expect 8 available units
* Call the MCP tool with the same warehouse, SKU, caller and stock snapshot; expect the same quantity
* Test zero availability, unknown SKUs and callers without warehouse access through both interfaces; verify denied requests return no stock data
* Change the quarantine rule in a fixture and run the shared regression tests plus adapter tests in CI. Release both interfaces with the updated core; a shared library does not update already deployed binaries

The design succeeds when one business-rule change needs one implementation change, and both entry points produce the same domain result for the same authorised request.
