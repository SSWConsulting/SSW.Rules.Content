You learn from a handful of experts whose tools, posts and talks shape your work. Checking each person's repositories and blog every morning takes time. A daily digest that repeats old items soon becomes another message to ignore.

**Use a bot to follow their public work: record what exists once, then notify only about new releases or publications.** Keep the list short so each alert gives you something worth reading or trying.

<endIntro />

## Choose the simplest subscription that works

Start with 1–5 people whose work you use, then list their relevant public repositories and feeds. Follow selected work, rather than every action on every account.

A custom bot is useful when you need one feed across several people's releases, blogs and videos, with consistent filtering and duplicate suppression. If you only need one repository's releases, [GitHub's custom watch settings](https://docs.github.com/en/subscriptions-and-notifications/get-started/configuring-notifications#configuring-your-watch-settings-for-an-individual-repository) may be enough. An RSS reader can also track new posts without a custom bot. Keep those simpler options when they meet your needs.

For a bot, define what counts as a new item before choosing the automation tool:

* **Tools:** published releases from selected repositories; decide whether to include prereleases
* **Writing:** new posts from the author's official RSS feed
* **Talks:** new videos from selected public channels, using a supported feed or API

Skip stars, forks and routine commits unless they serve a specific learning goal. Use official feeds and APIs, respect their access terms, and leave a source out if you cannot access it through a supported method.

## Record a baseline, then send only new items

Use a scheduled workflow or a small service with persistent storage and a notification destination. The essential behaviour is the same whichever tool you choose:

1. **Baseline without notifying.** On the first successful read of each source, save the IDs of the items it already contains. Repeat this baseline step when adding a source, so an old archive does not arrive as new work.
2. **Check at a useful interval.** A daily check in your timezone is a reasonable starting point. Prefer supported event subscriptions when available; otherwise follow the provider's [polling, conditional-request and rate-limit guidance](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api).
3. **Compare stable IDs.** Store source plus item ID, not just the latest title or date. GitHub's [release list](https://docs.github.com/en/rest/releases/releases#list-releases) exposes release IDs; RSS items can provide a [GUID](https://www.rssboard.org/rss-specification#ltguidgtSubelementOfLtitemgt), with a canonical post URL as a fallback. Retrieve enough pages to cover the gap since the last successful check, so two releases between checks are both found.
4. **Send a concise alert.** Include the tool or publication, version or title, a short source-backed description, and a direct link for each new item. Use the original title if you cannot verify a summary. If no new items exist, send nothing.
5. **Record delivery.** Keep pending items until delivery succeeds, then mark them delivered. Use stable item keys to suppress duplicates on retries; check whether your destination supports idempotent delivery before assuming retries cannot repeat a message.

A failed source request is not an empty feed. Preserve its saved state, back off as instructed, and report repeated failures to the bot's owner separately from learning alerts. Store any required credentials in the automation tool's secret store, with only the permissions needed.

## Compare the same three days

Northwind's learning feed follows its fictional Demo Editor app. All releases and features in this example are invented. On Monday it starts with v2.3. Tuesday has no change. On Wednesday, v2.4 adds split panes and v2.5 adds theme packs.

Test this sequence before relying on the bot: first run sends nothing; an unchanged run sends nothing; two new items produce one alert containing both; rerunning sends nothing. Also test a failed fetch and a failed delivery so neither loses an item or resets the baseline.

## Keep the feed useful

Review the watch list periodically and remove sources you no longer read. Check the bot's health separately: silence should mean no new work, not an unnoticed broken integration. Alerts report what was published; read the source and assess it before installing a tool or adopting advice.

This complements [configuring GitHub notifications](/github-notifications), which controls GitHub activity notifications. A [team notifications channel](/have-a-notifications-channel) gives alerts a home, while [reviewing project history](/how-to-see-what-is-going-on-in-your-project) serves a different need: catching up on team activity. Bring useful discoveries to [weekly AI meetings](/weekly-ai-meetings) when relevant; the bot supplies candidates and people decide what is worth sharing.
