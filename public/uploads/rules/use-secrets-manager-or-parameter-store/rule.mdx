A database password ends up in a Lambda environment variable, a Terraform variables file or an ECS task definition. Everyone who can open the function's configuration can read it. It is in Git history for good, and changing it means a redeploy, so nobody ever changes it.

<endIntro />

AWS has two places to keep these values. They look alike, and teams often pick one for everything. That either leaves a password with no rotation or pays secret prices for a feature flag.

If you know Azure, Secrets Manager is the closest match to Key Vault secrets. Azure makes the same split between secrets and configuration. See [Do you use Configuration over Key Vault?](/config-over-keyvault)

## Choose by what the value is

| | Secrets Manager | Parameter Store |
| --- | --- | --- |
| Use it for | Database credentials, API keys, OAuth tokens, private keys | Endpoint URLs, resource IDs, tuning values |
| Rotation | Automatic. AWS runs it for supported services such as RDS, and a Lambda function does it for most others | None |
| Encryption | Always | Only the `SecureString` type |
| Largest value | 64 KB | 4 KB, or 8 KB on the advanced tier |
| Cost | Per secret each month, plus API calls | Standard tier is free for up to 10,000 parameters in each account and Region |

AWS's own advice is short: [credentials go in Secrets Manager](https://docs.aws.amazon.com/systems-manager/latest/userguide/systems-manager-parameter-store.html), configuration goes in Parameter Store. Feature flags have a third home, AWS AppConfig, which is the match for Azure App Configuration.

A `SecureString` parameter is acceptable for a low-risk value that never needs to rotate, when cost matters more than the extra features. It is not the place for a production database password.

## Keep the value out of everything else

**Lambda.** Do not put secrets in environment variables. Use the [AWS Parameters and Secrets Lambda Extension](https://docs.aws.amazon.com/lambda/latest/dg/with-secrets-manager.html). It reads from both stores and caches each value for 5 minutes by default, so you do not pay for an API call on every invocation.

**ECS.** Reference the secret in the task definition's `secrets` block, and ECS [injects it when the container starts](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/specifying-sensitive-data.html). A running task keeps the old value, so start new tasks after a rotation.

**Infrastructure as Code.** Do not write the value in code or variables. Terraform state [can hold secret values](https://developer.hashicorp.com/terraform/language/state/sensitive-data) too, so let AWS generate the secret where it can. For RDS, turn on [managed master user passwords](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/rds-secrets-manager.html). RDS creates the master password, stores it in Secrets Manager and rotates it every 7 days by default. Nobody has to choose it or type it.

## Control who can read each secret

Name secrets by environment and application, such as `prod/orders/db`. Then give each workload read access to its own secret and nothing else:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "secretsmanager:GetSecretValue",
      "Resource": "arn:aws:secretsmanager:ap-southeast-2:111122223333:secret:prod/orders/db-??????"
    }
  ]
}
```

AWS adds 6 random characters to the end of every secret ARN. The [`??????` wildcard](https://docs.aws.amazon.com/secretsmanager/latest/userguide/auth-and-access_iam-policies.html) matches them without matching other secrets that start with the same name.

* Attach this policy to the role of one workload. For ECS, that is the task execution role. See [Do you give each Lambda its own least-privilege role?](/give-each-lambda-its-own-role)
* To share a secret with another account, you need a resource policy on the secret and [a KMS key that you create](https://docs.aws.amazon.com/secretsmanager/latest/userguide/auth-and-access_examples_cross.html). The default key does not work across accounts
* CloudTrail records each call that reads a secret, so you can see who read it and when

## Better still, have no secret

A secret you do not have cannot leak. Before you store an AWS access key, check whether the workload can use a role. See [Do you use Microsoft Entra ID to give your workloads access to AWS?](/use-entra-id-to-access-aws)

If an AWS credential gets out, see [Do you know how to roll AWS credentials if they are exposed?](/roll-exposed-aws-credentials) For any other secret, change it in the system that issued it, then update the stored value.
