A regression test reassigns a Northwind invoice, fails an assertion, and exits. The next person testing in UAT sees the wrong assignee and raises a bug caused by the test itself.

Shared DEV and UAT environments are somebody else's workspace too. Automated scripts and AI-driven browser tests must restore what they change and account for anything they leave behind. Even opening a record can write data.

<endIntro />

## Reserve the test data before changing it

Prefer [isolated, disposable environments](/ephemeral-environments). When a shared environment is necessary:

* Use only records approved for testing. Confirm nobody is working on them, then reserve them for the run
* Reserve the affected scope too. A global toggle or shared record order can affect people using other records
* Record the original assignee, toggle value, or ordered record IDs **before the first change**. Keep this snapshot with the run so recovery does not depend on the script staying alive

If you cannot prevent concurrent edits, use isolated data. Restoring an old snapshot over somebody else's new work makes the damage worse.

## Restore state when the test fails too

Put changes and assertions inside a `try` block, with restoration in `finally` or the framework's always-run cleanup step. Read back the restored values before releasing the reservation. Resetting to a default is not the same as restoring the original value.

See [Microsoft's C# exception-handling reference](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/statements/exception-handling-statements#the-try-finally-statement) for `try`/`finally` behaviour. A killed process may never run cleanup. Use the saved snapshot to recover an interrupted run before reusing its records.

**Failed cleanup is a failed run.** Report the affected record and remaining changes. Attempt each independent cleanup action even if another fails, and preserve the original test failure alongside any cleanup errors.

## Allow-list the traces that may remain

Before the run, list the expected persistent effects: for example, one generated document and the audit entries for reassignment and restoration. Keep legitimate audit history; do not delete it to make a test appear clean.

Before any supposedly read-only exploration, check whether opening a record starts a timer, writes an audit row, or stamps "last viewed". Include those effects in the plan or use a different record or environment.

After cleanup, compare the remaining effects with the allow-list and include the result in the run report. Identify retained documents and audit entries by their IDs. Report unexpected effects even when the assertions pass. If an effect cannot be safely reversed, flag it for recovery rather than silently declaring the environment clean.
