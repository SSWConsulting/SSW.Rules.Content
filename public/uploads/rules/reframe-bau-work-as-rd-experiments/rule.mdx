Business-as-usual (BAU) work such as upgrades, updates and maintenance does not qualify as R&D. Bug fixes usually do not qualify either (see below). If a team's backlog is mostly this kind of work, it will have little R&D to report, even if the work is hard.

<endIntro />

Before you create a chore PBI, pause and ask: **could this be done in a new way that hasn't been done before?** If so, the way you do it can become the experiment.

## Change the question, not the work

Don't create an epic to complete the chore. Instead, create one to investigate a new, untested way of completing it.

  body={<>
    **Epic:** Upgrade an Angular app from version 10 to 20.
  </>}
  figurePrefix="bad"

<boxEmbed
  style="greybox"
  body={<>
    **Epic:** Establish whether an AI-powered technology uplift program can upgrade an Angular app from version 10 to 20.

    **Success benchmark:** Define it before you start, for example the app builds and its tests pass with no manual code changes.
  </>}
  figurePrefix="good"
  figure="Investigates a new way of doing the upgrade, with a way to judge the result"
/>

The upgrade still happens. The difference is that the team is now running an experiment on *how* to do it, and recording what it learns. See [Do you make your R&D experiment outcomes measurable?](/make-rd-experiment-outcomes-measurable).

## Be honest about what qualifies

Reframing only works when the new approach is genuinely uncertain. Don't relabel routine work to make it look like R&D.

* If the outcome is already known, it is BAU, not an experiment
* If you are fixing a bug inside one of your own experiments, it may still count as part of that experiment
* If you are unsure, record it and let whoever prepares the R&D report decide

Bugs are a grey area, so check with whoever prepares the report before counting them.
