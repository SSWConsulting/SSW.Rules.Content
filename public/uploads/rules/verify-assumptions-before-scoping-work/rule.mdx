A Product Backlog Item (PBI) says, "Add a Finland freight surcharge by inserting a row into the existing surcharge table." The team estimates a small data change, then discovers that the table does not exist. The requirement still matters, but the estimate covers the wrong work.

A detailed brief, especially one drafted by an AI agent, can make an assumption sound established. **Verify the assumptions that change the scope before estimating or designing the solution.** Record what the evidence supports and what remains unknown so the next developer can check the reasoning.

<endIntro />

## Check the premises that change the estimate

During [backlog refinement](/backlog-refinement-meeting), identify the claims that would materially change the work if they were wrong. Examples include an existing table, a reusable service, a data owner or an available API. Focus on these claims rather than auditing the whole application.

For each claim:

* **Find a primary source** - Search the code and alternative names, then read the relevant definitions, callers, migrations and configuration. A matching class name alone does not prove that the feature exists
* **Check the relevant system** - Use authorised read-only schema checks, representative data, logs or a safe reproduction when code alone cannot establish the claim. Record the source revision and, for runtime evidence, the environment and check date
* **Update the scope** - Mark the claim as verified, refuted or unverified. Keep, remove or revise the dependent tasks and explain why

No search matches means **unverified**, not absent: the feature may use another name, live in another service or differ in the deployed version. Keep sensitive data out of the PBI. Check [AI-generated findings](https://docs.github.com/en/copilot/concepts/prompting-and-context/prompt-engineering#review-copilots-output) against the cited sources yourself.

## Record the evidence beside the PBI

Keep a short record of the premise, evidence, scope decision and remaining unknowns with the PBI. Link to exact source locations or saved, sanitised results; "I checked the code" is not enough.

These matched examples use **example data** from a fictional Northwind implementation, revision `freight-demo-v1`.

## Resolve uncertainty before committing to the scope

Proceed when the scope-changing premises have evidence, the tasks reflect that evidence and any remaining assumptions are explicit. If a technical unknown still prevents a useful estimate, create a [time-boxed spike](/encourage-spikes-when-a-story-is-inestimable) with a specific question and expected evidence. Ask the Product Owner to resolve business-policy questions.

Use this record when you [review an AI coding plan](/review-ai-plans). For a suspected defect, follow the guidance on [verifying bug reports before planning a fix](/treat-bug-reports-as-hypotheses).
