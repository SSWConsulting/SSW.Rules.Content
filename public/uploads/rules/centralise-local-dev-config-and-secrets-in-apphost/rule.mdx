When each service needs a separate configuration edit, a fresh clone becomes a troubleshooting exercise. A changed API port leaves the web app pointing at yesterday's address.

For a solution that already uses [Aspire](/aspire), make the **AppHost the entry point for local development configuration**. Define dependencies and connect configuration sources there, then pass each service only the values it needs.

<endIntro />

## Replace scattered settings with explicit references

The following Northwind examples use **example data**. The API uses an existing development database and an Orders service key; the web app calls the API.

  style="greybox"
  body={<>
    `Northwind.Api/appsettings.Development.json` holds a copied database connection string. The API's own User Secrets hold `Orders:ApiKey`. `Northwind.Web/appsettings.Development.json` holds a copied `Api:BaseUrl` of `http://localhost:5101`.

    After the API port changes, the web app still calls port 5101. Onboarding requires finding and editing settings in multiple places.
  </>}
  figurePrefix="bad"
  figure="The web app keeps a copied API address that drifts from the running API"
/>
`Northwind.Api/Properties/launchSettings.json` after the port changes:

```json
{
  "profiles": {
    "http": {
      "commandName": "Project",
      "applicationUrl": "http://localhost:5201"
    }
  }
}
```

`Northwind.Web/appsettings.Development.json`, still used by its HTTP client:

```json
{
  "Api": {
    "BaseUrl": "http://localhost:5101"
  }
}
```

**Figure: The API listens on port 5201 while the web app's copied address still targets port 5101**

## Wire the AppHost once

Use the AppHost to describe the same dependencies. This example targets a C# AppHost on .NET 10 with **Aspire 13.6**; the snippets are verified with 13.6.4. The [Aspire SDK documentation](https://aspire.dev/get-started/aspire-sdk/) covers `Aspire.AppHost.Sdk`, the `Aspire.Hosting.AppHost` package, and project references. Reference `Northwind.Api` and `Northwind.Web` from `Northwind.AppHost` so the SDK generates `Projects.Northwind_Api` and `Projects.Northwind_Web`.

[Aspire prompts for unresolved parameter values](https://aspire.dev/fundamentals/external-parameters/) and can save them to the AppHost's User Secrets. For headless onboarding scripts or CI checks, the example adds an optional preflight that lists all missing inputs and exits non-zero before launching resources. Omit that custom preflight if the native interactive prompt meets your needs.

```csharp
// Northwind.AppHost/AppHost.cs
var checkOnly = args.Contains("--check-config");
var builder = DistributedApplication.CreateBuilder(
    args.Where(arg => arg != "--check-config").ToArray());

string[] requiredKeys =
    ["ConnectionStrings:northwind", "Parameters:orders-api-key"];
var missing = requiredKeys.Where(key =>
    string.IsNullOrWhiteSpace(builder.Configuration[key])).ToArray();

if (missing.Length > 0)
{
    foreach (var key in missing)
        Console.Error.WriteLine($"Missing: {key}");
    Console.Error.WriteLine("Source: Northwind - Local development");
    return 1;
}

if (checkOnly)
{
    Console.WriteLine("Required configuration is present.");
    return 0;
}

var database = builder.AddConnectionString("northwind");
var ordersKey = builder.AddParameter("orders-api-key", secret: true);

var api = builder.AddProject<Projects.Northwind_Api>("api")
    .WithReference(database)
    .WithEnvironment("Orders__ApiKey", ordersKey);

builder.AddProject<Projects.Northwind_Web>("web")
    .WithReference(api);

builder.Build().Run();
return 0;
```

**Figure: The local AppHost checks required inputs and injects each dependency explicitly**

[Aspire parameters](https://aspire.dev/fundamentals/external-parameters/) read `Parameters:orders-api-key`; `AddConnectionString("northwind")` reads `ConnectionStrings:northwind`. `AddConnectionString` references an existing database; it does not create or start one.

[`WithReference` injects configuration](https://aspire.dev/fundamentals/environment-variables/) appropriate to the resource: here, `ConnectionStrings__northwind` for the API and API endpoints for the web app. `WithEnvironment` maps the secret parameter to `Orders__ApiKey`, which .NET reads as `Orders:ApiKey`. AppHost configuration is not automatically copied into every child process.

`WithReference(api)` supplies endpoints; it does not configure the web app's HTTP client. Projects using [Service Defaults](https://aspire.dev/get-started/csharp-service-defaults/) already register service discovery for HTTP clients. For a minimal web project without Service Defaults, add the `Microsoft.Extensions.ServiceDiscovery` package and use:

```csharp
// Northwind.Web/Program.cs
var builder = WebApplication.CreateBuilder(args);
builder.Services.AddServiceDiscovery();
builder.Services.AddHttpClient("api", client =>
    client.BaseAddress = new Uri("https+http://api"))
    .AddServiceDiscovery();

var app = builder.Build();
app.MapGet("/orders", async (IHttpClientFactory clients) =>
    await clients.CreateClient("api").GetStringAsync("/orders"));
app.Run();
```

**Figure: The web app calls the API by its logical service name instead of a copied port**

[Service discovery](https://aspire.dev/fundamentals/service-discovery/) resolves that logical name to the injected endpoint. The example assumes the API exposes `/orders`.

## Separate committed defaults from development secrets

Commit non-sensitive defaults and dependency wiring. Keep service-owned settings, such as log levels, with the service; centralising configuration does not mean moving every setting into the AppHost.

Choose the configuration provider separately from AppHost composition. For shared, sensitive or frequently changing values, follow [Azure App Configuration for local development](/app-config-for-developer-settings), with secrets referenced from Key Vault. Keep that source authoritative instead of copying those credentials into local files.

Load the provider into the AppHost before the preflight runs, using the same configuration keys. Values injected into child processes are set at launch; services that need live refresh can retain their own provider.

For developer-specific or disconnected local work, use local credentials only when the team permits local storage. The Northwind example uses the **AppHost's** [.NET User Secrets](https://learn.microsoft.com/en-us/aspnet/core/security/app-secrets?view=aspnetcore-10.0), outside source control. For the example above, use this shape in the AppHost's Manage User Secrets editor:

```json
{
  "ConnectionStrings": {
    "northwind": "EXAMPLE_ONLY_REPLACE_WITH_DEVELOPMENT_CONNECTION_STRING"
  },
  "Parameters": {
    "orders-api-key": "EXAMPLE_ONLY_NOT_A_SECRET"
  }
}
```

**Figure: Both development inputs belong to the AppHost's secret store; these placeholders are example data**

Use an AppHost launch profile with `DOTNET_ENVIRONMENT=Development`. If the project has no `UserSecretsId`, initialise it with `dotnet user-secrets init --project Northwind.AppHost`. Replace the placeholders with authorised development values. User Secrets are unencrypted local storage for development; `secret: true` describes a sensitive parameter and does not encrypt its source or protect a committed value. Never print secret values when checking configuration.

If an approved offline workflow needs a shared development credential, keep one access-controlled record, such as **Northwind - Local development**, and update it when keys change or credentials rotate. Keep individually issued credentials individual. Follow [sharing developer secrets securely](/share-your-developer-secrets-securely) for the sharing mechanism and [storing secrets securely](/store-your-secrets-securely) for deployment storage. Production uses its own secret provider and credentials.

## Check the setup before starting services

This preflight is for a local development AppHost. If the same AppHost also models deployment, validate deployment inputs separately instead of requiring local User Secrets.

The AppHost code above implements `--check-config`; it is **a project-defined switch**, not an Aspire command. Keep `requiredKeys` in step with every required `AddParameter` and `AddConnectionString` input. Run it from the solution directory:

```shell
dotnet run --project Northwind.AppHost -- --check-config
```

With both inputs missing, it writes:

```text
Missing: ConnectionStrings:northwind
Missing: Parameters:orders-api-key
Source: Northwind - Local development
```

**Figure: All missing input names appear together without printing secret values or starting services**

The check returns a non-zero exit code when either required input is missing or blank. A pass confirms presence only; it does not validate credentials, database availability, or placeholder values.

As an onboarding check, use a fresh clone, obtain the authorised development values, run the check, then start the AppHost with `dotnet run --project Northwind.AppHost`. Verify that the web app reaches the API and the API reaches its dependencies without editing per-service files. Document this path as part of the [initial developer experience](/developer-experience). A service launched outside the AppHost still needs its own configuration source.
