Draft Pull Requests show work in progress so teammates can collaborate and give feedback early. They help improve code quality, reduce duplicate work, and make ongoing changes visible. Draft Pull Requests can also trigger GitHub Workflows, giving developers early feedback when the workflows are configured to run on drafts.

<endIntro />

## Why Draft Pull Requests?

* Clearly communicate that the change is still a work in progress and not yet ready for review.
* Prevent unnecessary notifications to the team (for example, "Sam opened a pull request") when the work is still in progress.
* In the age of AI, pull requests created by tools such as Claude or Copilot should start as drafts so a human can validate the changes before involving reviewers.
* Control which CI automations run by using draft pull requests, avoiding unnecessary builds, deployments, or long-running test suites until the work is ready.

## Verify compatibility before marking ready

Before handing the PR to reviewers, check that it works with current `main`:

1. **Fetch `main`.** Inspect changes in the areas the PR touches. Remove redundant work if `main` already solves the problem.
2. **Update the feature branch.** Follow the repository's merge or rebase convention, coordinate any shared history changes, and resolve textual conflicts.
3. **Check semantic compatibility.** Renamed APIs, changed contracts, overlapping work, and migrations can break behaviour even when Git combines the text cleanly. Check migrations in disposable environments.
4. **Test the combined revision.** Restore dependencies, rebuild, and run relevant tests. Confirm CI covers the updated revision or its test merge. An old green run or a skipped draft suite does not verify the new combination.
5. **Record the evidence.** In the PR description, list the tested `main` and PR commits, links to check results, manual verification, and remaining limits. Fetch again before handoff; if `main` advances, update the branch and repeat affected checks.

Leave the PR in draft if verification is blocked, and state the blocker in the PR description.

Readiness is a point-in-time check. Use [branch protection](/protect-your-main-branch) to enforce integration requirements as `main` moves during review.

## Clearly marking your Pull Requests

A draft status can be easy to overlook on GitHub. Add a title prefix like `🚧 WIP: &#123;&#123;PR Title&#125;&#125;` to make work in progress easier to spot.
