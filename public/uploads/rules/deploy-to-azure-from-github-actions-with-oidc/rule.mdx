Your pipeline logs in to Azure with a service principal client secret saved as a GitHub secret. That secret is a long-lived password to your production subscription. It can leak through a compromised workflow, a copied repository or a careless log line. It expires at the worst possible time and breaks every deployment. And someone has to remember to rotate it.

<endIntro />

OpenID Connect (OIDC), also called workload identity federation, removes the secret altogether. GitHub issues a short-lived token for each workflow run, and Azure trusts it because you told Entra ID which repository and environment it may come from. There is no password to store, leak, rotate or expire.

## Why OIDC instead of a client secret

* **Nothing to steal** - there is no credential stored in GitHub. A leaked workflow file or repository copy gives an attacker nothing they can use elsewhere
* **Nothing to rotate** - no expiry date to track, and no outage when a secret quietly expires
* **Short-lived** - the token is valid for a single run
* **Scoped** - the trust is limited to one repository and one environment, so a fork or another branch cannot use it
* **Auditable** - Azure sign-in logs show which repository and workflow signed in

## How to set it up

### 1. Create the identity in Azure

Create an app registration (or a user-assigned managed identity) for the deployment, and give it the least privilege it needs, for example Contributor on a single resource group instead of the whole subscription. Do not create a client secret for it.

### 2. Add a federated credential

On the app registration, add a federated credential for GitHub Actions. The subject says exactly what is trusted:

| Setting  | Value                                          |
| -------- | ---------------------------------------------- |
| Issuer   | `https://token.actions.githubusercontent.com`  |
| Subject  | `repo:YourOrg/YourRepo:environment:production` |
| Audience | `api://AzureADTokenExchange`                   |

Scope the subject to a GitHub **environment**, not just the repository. Then the environment's protection rules (required reviewers, allowed branches) decide who can deploy.

### 3. Protect the GitHub environment

In the repository settings, create the environment (for example `production`), limit it to protected branches, and require a pull request approval before a deployment starts.

### 4. Log in from the workflow

Give the job permission to request a token, name the environment, and pass the identifiers to `azure/login`. There is no `AZURE_CREDENTIALS` and no secret key.

```yaml
permissions:
  id-token: write
  contents: read

jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: production
    steps:
      - uses: actions/checkout@v4

      - uses: azure/login@v3
        with:
          client-id: ${{ secrets.AZURE_CLIENT_ID }}
          tenant-id: ${{ secrets.AZURE_TENANT_ID }}
          subscription-id: ${{ secrets.AZURE_SUBSCRIPTION_ID }}

      - run: az webapp deploy --resource-group my-rg --name my-app --src-path ./app.zip
```

**✅ Figure: Good example - The workflow signs in with a short-lived token. The three IDs identify the app but are not credentials**

```yaml
- uses: azure/login@v1
  with:
    creds: ${{ secrets.AZURE_CREDENTIALS }}
```

**❌ Figure: Bad example - AZURE\_CREDENTIALS holds a client secret that works from anywhere until it expires or someone rotates it**

## When you still need something else

* Targets that cannot use federation (some third-party services) still need a secret. Keep it in a vault and see [Do you use enterprise secrets in your DevOps pipelines?](/enterprise-secrets-in-pipelines)
* Code that runs inside Azure (an App Service or a Function) should use a managed identity at runtime, not a federated credential. See [Do you use Managed Identity in Azure?](/use-managed-identity-in-azure)
