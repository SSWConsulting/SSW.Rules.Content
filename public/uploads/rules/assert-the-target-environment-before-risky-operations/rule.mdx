A Northwind maintenance command deletes old Orders successfully. Unfortunately, a stale connection string points it at the wrong database. A successful exit code does not mean the right data changed.

**Make the command prove its target before it touches the database.** A warning printed after the first query is too late.

<endIntro />

## Check intent and destination independently

For a production-only command, require all of these to agree:

* **Explicit intent** - Require `TARGET_ENV=prod`; never default to production
* **Exact server** - Match the parsed server name against an approved endpoint, not a substring such as `prod`
* **Exact database** - Require the expected database name, even when the server is correct
* **Every source** - Validate all connections before opening any of them; one correct source does not make the others safe

Keep the expected targets in reviewed code or a separately controlled allow-list. Deriving the expected server from the same connection string makes the check meaningless. Give each source its own expected target if the command spans databases.

## Refuse before the first side effect

Put the guard at the command's entry point, before opening connections, taking locks or running any SQL. Missing, malformed or mismatched settings must stop execution with a named error and a non-zero exit code.

```csharp
using var connection = new SqlConnection(
    Environment.GetEnvironmentVariable("NORTHWIND_ORDERS_CONNECTION"));
connection.Open();
using var command = connection.CreateCommand();
command.CommandText = "DELETE FROM Orders WHERE OrderDate < '2000-01-01'";
command.ExecuteNonQuery();
```

**❌ Figure: Bad example - The command deletes Orders from whichever database the loaded connection string selects**

The following guard checks two Northwind sources without connecting to either:

```csharp
using Microsoft.Data.SqlClient;

const int NOT_PROD_TARGET = 20;
var sources = new[]
{
    Environment.GetEnvironmentVariable("NORTHWIND_ORDERS_CONNECTION"),
    Environment.GetEnvironmentVariable("NORTHWIND_CUSTOMERS_CONNECTION")
};

bool MatchesProdTarget(string? connectionString)
{
    if (string.IsNullOrWhiteSpace(connectionString)) return false;

    try
    {
        var target = new SqlConnectionStringBuilder(connectionString);
        return string.Equals(target.DataSource, "northwind-sql-prod",
                   StringComparison.OrdinalIgnoreCase)
            && string.Equals(target.InitialCatalog, "Northwind",
                   StringComparison.Ordinal);
    }
    catch (ArgumentException)
    {
        return false;
    }
}

if (Environment.GetEnvironmentVariable("TARGET_ENV") != "prod"
    || !sources.All(MatchesProdTarget))
{
    Console.Error.WriteLine(
        "NOT_PROD_TARGET: expected prod / northwind-sql-prod / Northwind; no SQL executed.");
    return NOT_PROD_TARGET;
}

// Database work follows here, using the validated strings in sources.
return 0;
```

**✅ Figure: Good example - The guard rejects an incorrect environment or either incorrect source before opening a connection**

Use the validated values for execution; reloading configuration afterwards can change the destination. Report the failed check without logging credentials or the full connection string. See Microsoft's [connection string builders](https://learn.microsoft.com/en-us/sql/connect/ado-net/connection-string-builders) for parsing details.

## Prove the refusal locally

Test the guard with fake connection strings and a spy for database access. Missing `TARGET_ENV`, a wrong server, a wrong database, a malformed string or a mismatched second source must each produce `NOT_PROD_TARGET` and **zero database calls**. Also test that all matching values let execution proceed.

Before using a real database, rehearse the whole command against a disposable local Northwind database with a separate sandbox target map. A successful sandbox run tests the operation; the refusal tests prove the guard runs first. Keep the production checks enabled when promoting the command.
