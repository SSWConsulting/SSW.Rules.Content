Your AI feature needs data the model was never trained on - your codebase, your support docs, your policies - and it is bigger than the prompt you can send. How the model reaches it sets your cost per query, your latency, and whether an answer can cite a source.

<endIntro />

## Long context

The newest of the three, and the one to try first. Context windows reaching a million tokens turned "just put it all in the prompt" from a thought experiment into a real option - no index, no embedding pipeline, no sync job, and it is the only strategy that reasons across the whole corpus at once.

It has two failure modes worth knowing before you rely on it. Accuracy [sags in the middle](https://arxiv.org/abs/2307.03172) of a long window. And on multi-hop questions, performance [collapses to the least visible fact](https://arxiv.org/abs/2601.12499) - one badly-positioned hop takes the whole chain with it - though reasoning models largely recover it. A bigger window is not a substitute for choosing what goes in it.

## Vector retrieval (RAG)

Embed, search, inject the matches. Best for large unstructured prose: support docs, PDFs, policies, transcripts. SSW's [RulesGPT](https://rulesgpt.ssw.com.au) works this way, and so does Cursor - it [chunks your repo and keeps the embeddings in a vector DB](https://cursor.com/blog/secure-codebase-indexing), the opposite call to Claude Code on the same problem.

### "RAG is dead" is not quite right

Retrieval as a **default pipeline** - chunk, embed, top-k, stuff the prompt - is no longer a sensible starting point. Retrieval as a **capability** is fine. Claude Projects [switches RAG on](https://support.claude.com/en/articles/11473015-retrieval-augmented-generation-rag-for-projects) when a project outgrows the context window, then back off when it shrinks. And even the [best result for ditching the vector store](https://arxiv.org/abs/2602.23368) puts agentic search at roughly 90% of RAG's scores, not ahead of them.

## Agentic search

Hand the model `glob`, `grep` or a query API and let it look. Nothing to index, so nothing goes stale and permissions come from the access path. [Claude Code dropped its vector store](https://www.latent.space/p/claude-code) for this. Costs latency, and weakens when the answer uses different words to the question (`retry` vs `backoff` vs `circuit_breaker`).

## Check the cache before you commit

If the corpus comfortably fits the window and every user sees the same thing, put it in the prompt - there is nothing to build.

Long context stays cheap only while one prefix is reused enough to amortise caching it. **Per-user document sets** break that - a separate prefix per tenant - and so does a corpus that changes faster than you reuse it. Either way, the prompt you thought was cheap is near full price on every request. See [prompt caching](/do-you-follow-best-practices-for-prompt-caching).

| | Long context | RAG | Agentic search |
| --- | --- | --- | --- |
| **Best for** | Small, static, shared | Large prose corpora | Structured, live, permission-sensitive |
| **Infrastructure** | None | Vector DB, embeddings, reranker, sync | Tools you already have |
| **Auditability** | Weak | Strong - chunks are citable | Strong - query is in the log |
| **Weak spot** | Middle-of-context accuracy | Stale index, vocabulary mismatch | Latency and tokens |
