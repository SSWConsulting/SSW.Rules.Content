A new developer joins the project and starts their AI coding agent. It asks for permission to run the build. Then the tests. Then the linter. They click "allow" forty times on the first day, and by the afternoon they click it without reading. Meanwhile nothing stops the agent from opening the `.env` file, because the instruction "never read secrets" is only a sentence in `AGENTS.md`.

Instructions tell an agent what you want. They don't stop it. What the agent is actually allowed to do is decided by its settings file, and most teams leave that on each developer's machine.

<endIntro />

Commit a settings file to the repository. Everyone who clones the project then gets the same permissions, the same hooks and the same tools from the first session.

`AGENTS.md` and the settings file do different jobs:

* **Instructions** (`AGENTS.md`, `CLAUDE.md`) - Guidance the agent reads and usually follows. See [Do you write an AGENTS.md?](/write-agents-md)
* **Settings** - Rules the tool enforces. A denied command doesn't run, whatever the agent thinks about it

## What goes in the shared settings file?

* **Allowed commands** - The safe things everyone runs all day: build, test, lint, read-only Git commands. No more approval prompts for these
* **Denied commands and files** - Secrets, `.env` files, destructive commands. A deny rule beats an allow rule
* **Commands that always ask** - Pushing, deploying, running database migrations
* **Hooks** - Scripts that run on agent events, for example formatting a file after every edit or blocking a dangerous command
* **MCP servers** - The servers the project uses, so everyone has the same tools
* **Sandbox settings** - Which folders the agent can write to and which domains it can reach

## What stays out of it?

* **Secrets and tokens** - Never. Reference an environment variable instead
* **Personal preferences** - Your model, theme and editor choices
* **Machine-specific paths and ports**
* **Wide-open permissions** - "Allow everything" in a shared file turns off the safety checks for the whole team

Personal settings go in a local override that Git ignores. This is the same idea as [Do you add a local configuration file for developer-specific settings?](/add-local-configuration-file-for-developer-specific-settings)

## Where does each tool keep its settings?

| | Claude Code | OpenAI Codex | GitHub Copilot CLI | GitHub Copilot in VS Code |
| --- | --- | --- | --- | --- |
| **Shared (commit)** | `.claude/settings.json` | `.codex/config.toml` | `.github/copilot/settings.json` | `.vscode/settings.json` |
| **Personal for this project (gitignore)** | `.claude/settings.local.json` | - | `.github/copilot/settings.local.json` | - |
| **Personal for all projects** | `~/.claude/settings.json` | `~/.codex/config.toml` | `~/.copilot/settings.json` | VS Code user settings |
| **Command rules** | `permissions` with `allow`, `ask` and `deny` | `approval_policy`, `sandbox_mode` and `.codex/rules/` | Allow and deny tool flags | Terminal auto-approve settings |
| **Hooks** | `hooks` in the settings file | `.codex/hooks.json` | `.github/hooks/` | Preview |
| **MCP servers** | `.mcp.json` | `mcp_servers` in the config file | `.mcp.json` | `.vscode/mcp.json` |

The Copilot cloud agent is configured differently. Its environment is set up by `.github/workflows/copilot-setup-steps.yml`, and its firewall and MCP servers are set in the repository settings on GitHub.

File names and keys change often. Check the product documentation under [Learn more](#learn-more) before you copy an example.

`.claude/settings.json` (committed)

```json
{
  "permissions": {
    "allow": ["Bash(npm run *)", "Bash(git status)", "Bash(git diff *)"],
    "ask": ["Bash(git push *)"],
    "deny": ["Read(./.env)", "Read(./.env.*)", "Read(./secrets/**)"]
  }
}
```

**✅ Figure: Good example - The same rules as settings. The tool enforces them for everyone who clones the repository**

Claude Code checks deny rules first, then ask, then allow. A deny rule in any settings file can't be undone by an allow rule in another one.

### OpenAI Codex

Codex reads a project `.codex/config.toml` next to your user configuration:

```toml
approval_policy = "on-request"
sandbox_mode = "workspace-write"

[sandbox_workspace_write]
network_access = false
```

Rules for individual commands go in `.codex/rules/`.

### GitHub Copilot

Copilot CLI reads `.github/copilot/settings.json` from the repository, with `settings.local.json` beside it for your own overrides. Hooks in `.github/hooks/` apply to both the CLI and the cloud agent. In VS Code, agent settings sit with the other workspace settings in `.vscode/settings.json`, and MCP servers go in `.vscode/mcp.json`.

## What are the gotchas?

### Shared settings need a trusted folder

A settings file in a repository you just cloned could have been written by anyone. Claude Code and Codex both ask you to trust a project before they apply everything in it. Until you do, Codex skips the project's `.codex/` folder, and Claude Code applies the deny and ask rules but not the allow rules. Tell new team members to expect the trust prompt.

### Review changes to the settings file like code

A new allow rule gives every agent on the team a new power. Read the diff of a settings file as carefully as you read a change to the build pipeline, and be suspicious of a pull request that widens permissions without explaining why.

### One tool's settings don't apply to another

If your team uses more than one agent, each needs its own file. Keep them in step: when you deny reading secrets in one, deny it in the others.

### Your organization can set rules above the repository

All three tools support managed settings that an administrator pushes to every machine, and those win over the repository file. Use them for rules that must hold in every project, such as blocked commands or approved MCP servers. Use the repository file for what is specific to the project.
