Reading unfamiliar code line by line can obscure the main flow. Start with the software's purpose and structure, then work towards the implementation details.

Before reading the code, build this foundation:

1. **Basic knowledge** - Learn the basics of the languages and underlying technologies
2. **Software function** - Understand the features and configuration. Read the user manual, then run the software and try it yourself
3. **Relevant documentation** - Read the README, release notes, design documents and wiki for context and design decisions. Where documentation is missing, ask the original authors if available
4. **The structure of the code** - Identify the purpose of each directory. A familiar structure, such as [Clean Architecture](https://github.com/jasontaylordev/CleanArchitecture), can make navigation easier

## Peel the onion

Read from the big picture down to the details:

1. **[Interface/abstract definition](/interfaces-abstract-classes)** - Identify the data structures and business entities described by interfaces or abstract definitions, and understand their relationships
2. **Glue code** - Find how modules connect through middleware, promises, callbacks, proxies, delegation or dependency injection. These connections can spread a single flow across several places in the code
3. **Business process** - Trace the main business flow and how data moves through it before investigating details. Draw a flowchart when it helps explain the sequence
4. **Detailed implementation** - With the structure and main flow established, focus on the relevant implementation:
   * **Code logic** - Distinguish business rules from control flow. Mixing the two can make code harder to follow
   * **Error handling** - Error paths can occupy much of an implementation. The 20/80 split suggested by the Pareto principle is a rough heuristic, not a measured ratio for every codebase. Temporarily hide error paths in the editor, or comment them out in a disposable reading copy, to trace the main path. Return to them to understand failure behaviour, and keep them intact in code you run or commit
   * **Data processing** - Defer routine data manipulation while tracing the main flow, then inspect transformations that affect the behaviour you are investigating
   * **Important algorithms** - Identify core algorithms, such as indexing, unique identifier generation, recommendations or statistics. These may need closer study to understand the implementation
   * **Low-level interaction** - For code that interacts with the operating system or hardware, learn the relevant system concepts before investigating the details
5. **Runtime debugging** - Run the code and use logs, breakpoints and tracing to check your understanding of its execution

Keep these habits in mind:

* Use the top-down, general-to-detail approach known as "Peeling the Onion"
* Sketch flowcharts, call sequences or module diagrams to clarify relationships
* Separate kinds of logic and set aside distracting details while following the main path
* Debug and trace execution to test your understanding

## Match dependency source to the installed version

The default branch may describe behaviour that is absent from the installed package. Match the source to the version you are investigating before drawing conclusions.

1. **Define the question** - Record the behaviour you want to explain, the runtime and relevant settings
2. **Find the resolved version** - Check the restored dependency graph or lockfile, including transitive dependencies. A declared version range does not identify the exact version in use
3. **Match the source** - Read the documentation and release notes for that version, then follow the public API into source and tests at the matching release tag or commit. Matching symbols and [Source Link](https://learn.microsoft.com/en-us/dotnet/standard/library-guidance/sourcelink) can help locate original .NET source. Record uncertainty if you cannot establish the match
4. **Test a minimal probe** - Use synthetic inputs, such as Northwind sample data, with the resolved package version and relevant settings, and without production connections or credentials. Compare expected and actual output. Check whether a supported option explains the result before proposing a patch. One passing input establishes only that case
5. **Keep the evidence** - Save the question, versions, source permalinks, runnable probe and conclusion with the investigation

If an implementation gap remains, check the licence terms before decompiling and investigate only that gap. Verify reconstructed code against the running package.
