CI/CD pipelines automate building, testing, and deploying code. Before a production deployment, a human reviewer needs a chance to assess the changes and stop a release with known issues. A deployment gate pauses the pipeline until that review is complete.

<endIntro />

GitHub adds manual approval steps to workflows through the [environments](https://docs.github.com/en/actions/deployment/targeting-different-environments/using-environments-for-deployment) feature.

Environments also support per-environment secrets, timers, and protection rules. Feature availability depends on repository visibility and plan:

* **Public** - environments are available on all current GitHub plans
* **Private** - environments are available. Environment secrets and deployment branch policies need a paid plan; **Required reviewers need GitHub Enterprise Cloud**

Only repository administrators can configure environment reviewers, timers, and secrets.

When a deployment job references an environment with required reviewers, GitHub pauses the job and notifies the reviewers. A reviewer can approve or reject the deployment and add comments. After approval, the job continues.

GitHub will also display the review information in the deployment summary.

## Example workflow

Most projects use multiple environments such as `dev`, `staging`, and `prod`. You can add as many environments as needed to suit your team or project.

Here is a high-level workflow for building and deploying a project:

1. In parallel:
   * Build the .NET WebAPI application
   * Build the UI application
   * Run unit tests
2. Automatically deploy the applications to `dev`
3. After review and manual approval by Release Master, deploy the applications to `staging`
4. After review and manual approval by Release Master, deploy the applications to `prod`

The Release Master uses approvals to control which changes reach `staging`, so new deployments do not disrupt testing.

Before approving a deployment to `prod`, the Release Master checks for known issues that could affect users.

## Enforce human ownership for agent-assisted releases

An agent can prepare a release without owning every step needed to ship it. Make the boundary enforceable through permissions and gates:

* **Separate identities:** Give the agent its own identity without the release owner's credentials, reviewer membership, or administrative access.
* **Assign ownership:** For each reserved release step, record the human owner, the control that enforces the boundary, and the evidence needed to confirm completion.
* **Choose the handoff:** Use **Human approval** when a pipeline deploys the approved artifact after a person approves it. Use **Human-only execution** when the person must perform the action. Review alone is insufficient if the agent can still merge or publish afterward.
* **Gate production:** Require a human reviewer, prevent self-review, and disable administrator bypass where supported. The deployment job must reference the protected environment, with production credentials behind its gate. Remove alternative deployment credentials from the agent and protect changes to the gate itself. See [GitHub environment controls](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments).
* **Protect other reserved actions:** A deployment gate does not cover a separate package-publishing job, release-branch merge, secret rotation, or customer announcement. Restrict each action at its destination, accounting for inherited roles, workflow access, registry tokens, and connected sessions.
* **Hand over explicitly:** Let the agent prepare artifacts, then report **Awaiting human action** with the exact version, evidence links, remaining action, and responsible role.
* **Verify the boundary:** In a disposable project with equivalent controls, use the agent's actual identity to check that each reserved operation is denied or waits for human approval, as intended. Confirm that the human path deploys only the reviewed artifact. Recheck after permission changes.
