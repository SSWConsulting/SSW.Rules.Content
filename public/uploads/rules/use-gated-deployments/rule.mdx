CI/CD pipelines automate building, testing, and deploying code. Before a production deployment, a human reviewer needs a chance to assess the changes and stop a release with known issues. A deployment gate pauses the pipeline until that review is complete.

<endIntro />

GitHub adds manual approval steps to workflows through the [environments](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments) feature.

Environments also support per-environment secrets, timers, and protection rules. Feature availability depends on repository visibility and plan:

* **Public** - environments are available on all current GitHub plans
* **Private** - environments, environment secrets, and deployment branch policies require GitHub Pro, Team, or Enterprise; **required reviewers need GitHub Enterprise Cloud**

Only repository administrators can configure environment reviewers, timers, and secrets.

When a deployment job references an environment with required reviewers, GitHub pauses the job and notifies the reviewers. A reviewer can approve or reject the deployment and add comments. After approval, the job continues.

GitHub will also display the review information in the deployment summary.

## Example workflow

Most projects use multiple environments such as `dev`, `staging`, and `prod`. You can add as many environments as needed to suit your team or project.

Here is a high-level workflow for building and deploying a project:

1. In parallel:
   * Build the .NET WebAPI application
   * Build the UI application
   * Run unit tests
2. Automatically deploy the applications to `dev`
3. After review and manual approval by a required reviewer, deploy the applications to `staging`
4. After review and manual approval by a required reviewer, deploy the applications to `prod`

The required reviewer uses approvals to control which changes reach `staging`, so new deployments do not disrupt testing.

Before approving a deployment to `prod`, the required reviewer checks for known issues that could affect users.

## Apply the gate to agent-assisted releases

An agent can prepare a release while a human controls approval of the production deployment:

* **Separate identities:** Give the agent its own identity without the release owner's credentials, reviewer membership, or administrative access.
* **Gate production:** Make the deployment job reference the protected production environment, with deployment credentials behind its human approval gate. Prevent self-review and administrator bypass where supported; protect changes to the gate and give the agent no alternative deployment credentials.
* **Hand over explicitly:** Report **Awaiting human action** with the exact version, evidence links, remaining action, and release owner. State whether the human approves the pipeline deployment or must perform the action themselves.

Verify the boundary in a disposable project with equivalent controls, using the agent's actual identity: deployment must wait for human approval, and the approved path must deploy only the reviewed artifact. Recheck after permission changes. A deployment gate does not protect separate actions such as package publishing or release-branch merges; restrict those separately when they are reserved for a human.
