An API starts with a handful of endpoints, and giving each one its own permission feels precise. A year later there are 300 endpoints, 300 permissions, a token stuffed with permission claims, and an admin who has to tick 40 boxes to let someone view and update teams. Nobody can say for sure what a group is allowed to do, and every new endpoint means another permission to create, assign and remember.

<endIntro />

Instead, give each feature area (module) a small, fixed set of permission buckets, and make every endpoint require one of them:

* `module:read` - View data
* `module:write` - Create and change data as part of normal day-to-day work
* `module:manage` - Administrative or high-impact actions, such as deleting, disbanding, or changing who has access

Groups are granted buckets, and endpoints check buckets. Access becomes easy to explain ("Mission coordinators can write teams"), easy to audit, and new endpoints usually need no new permission at all.

## Don't create one permission per endpoint

```csharp
var group = app.MapGroup("/api/teams");

group.MapGet("/", GetAllTeams).RequireAuthorization("teams.get-all");
group.MapGet("/{teamId:guid}", GetTeam).RequireAuthorization("teams.get-by-id");
group.MapPost("/", CreateTeam).RequireAuthorization("teams.create");
group.MapPost("/{teamId:guid}/heroes/{heroId:guid}", AddHeroToTeam).RequireAuthorization("teams.add-hero");
group.MapPost("/{teamId:guid}/execute-mission", ExecuteMission).RequireAuthorization("teams.execute-mission");
group.MapPost("/{teamId:guid}/complete-mission", CompleteMission).RequireAuthorization("teams.complete-mission");
group.MapDelete("/{teamId:guid}", DisbandTeam).RequireAuthorization("teams.disband");
```

**❌ Figure: Bad example - Every endpoint has its own permission, so policies, claims and group assignments grow with every endpoint you add**

A permission-per-endpoint model looks granular, but it causes:

* **Policy sprawl** - Every endpoint needs its own policy registration and its own name to keep in sync
* **Large tokens** - When permissions are issued as claims, every permission a user holds ends up in their token, adding size to every request
* **Hard assignment** - Admins have to understand individual endpoints to give someone sensible access
* **Gaps** - A new endpoint is easy to ship before anyone grants its permission, or with a copy-pasted permission that is wrong

## Classify every endpoint into a bucket

Define the permissions once, in one place, using a consistent `module:action` format. Register a named policy per bucket, then attach those policies to your endpoints.

```csharp
public static class Permissions
{
    public const string ClaimType = "permission";

    public static class Teams
    {
        public const string Read = "teams:read";
        public const string Write = "teams:write";
        public const string Manage = "teams:manage";
    }
}

builder.Services.AddAuthorizationBuilder()
    .AddPolicy(Permissions.Teams.Read, policy => policy.RequireClaim(Permissions.ClaimType, Permissions.Teams.Read))
    .AddPolicy(Permissions.Teams.Write, policy => policy.RequireClaim(Permissions.ClaimType, Permissions.Teams.Write))
    .AddPolicy(Permissions.Teams.Manage, policy => policy.RequireClaim(Permissions.ClaimType, Permissions.Teams.Manage));

var group = app.MapGroup("/api/teams");

group.MapGet("/", GetAllTeams).RequireAuthorization(Permissions.Teams.Read);
group.MapGet("/{teamId:guid}", GetTeam).RequireAuthorization(Permissions.Teams.Read);
group.MapPost("/", CreateTeam).RequireAuthorization(Permissions.Teams.Write);
group.MapPost("/{teamId:guid}/heroes/{heroId:guid}", AddHeroToTeam).RequireAuthorization(Permissions.Teams.Write);
group.MapPost("/{teamId:guid}/execute-mission", ExecuteMission).RequireAuthorization(Permissions.Teams.Write);
group.MapPost("/{teamId:guid}/complete-mission", CompleteMission).RequireAuthorization(Permissions.Teams.Write);
group.MapDelete("/{teamId:guid}", DisbandTeam).RequireAuthorization(Permissions.Teams.Manage);
```

**✅ Figure: Good example - Seven endpoints share three bucket permissions, and the next "read" endpoint needs no new permission**

Make the buckets cumulative: `manage` includes `write`, and `write` includes `read`. Expand a bucket into the buckets below it when you build the user's permissions (for example, when issuing the token), so a group only needs the single highest bucket it should have.

Back the policies with tests that call each endpoint without a token, with the wrong bucket, and with the right bucket, and check for 401, 403 and success.

## Split manage into sub-permissions when you need finer control

Sooner or later, someone needs to do one administrative action without getting all of `manage`. For example, a mission coordinator should be able to abort a mission that has gone wrong, but not disband a team or change who has access to the module.

Don't solve this with a growing pile of unrelated one-off permissions. Instead, break `manage` into named sub-permissions, and make `manage` a roll-up grant that resolves to all of them:

* Endpoints check the specific sub-permission (for example, `teams:disband`), never `teams:manage` directly
* Granting `teams:manage` still gives every sub-permission, including ones added later, so existing groups need no re-assignment
* Granting a single sub-permission gives only that action - it does not pull in `write` or `read` as well

```csharp
public static class Teams
{
    public const string Read = "teams:read";
    public const string Write = "teams:write";
    public const string Manage = "teams:manage"; // Roll-up grant only - no endpoint checks this

    public const string Disband = "teams:disband";
    public const string AbortMission = "teams:abort-mission";
    public const string ManageAccess = "teams:manage-access";
}

// When building the user's permissions, a full "manage" grant expands to every sub-permission
private static readonly Dictionary<string, string[]> SubPermissions = new()
{
    [Teams.Manage] = [Teams.Disband, Teams.AbortMission, Teams.ManageAccess],
};

group.MapDelete("/{teamId:guid}", DisbandTeam).RequireAuthorization(Permissions.Teams.Disband);
group.MapPost("/{teamId:guid}/abort-mission", AbortMission).RequireAuthorization(Permissions.Teams.AbortMission);
```

**✅ Figure: Good example - Each high-impact action can be granted on its own, while "manage" still covers everything**
