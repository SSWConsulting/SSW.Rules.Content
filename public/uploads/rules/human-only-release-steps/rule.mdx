An AI agent can prepare a release, pass every test, and still lack authority to ship it. If the checklist says only "release the new version", the agent may treat merging, publishing and notifying customers as ordinary follow-up work.

**Mark the release steps reserved for people, name their owners, and enforce each boundary in the platform that performs the action.** Document the same boundary in the release checklist and agent instructions. A sentence asking the agent to stop is useful guidance, but it does not remove its credentials or permissions.

<endIntro />

## Define what remains with a person

The release owner decides which actions need human judgement for this product. Common candidates include approving production deployments, merging to a release branch, publishing a package version, rotating production secrets and sending customer announcements. Reserve the actions that warrant it; build, test and release preparation can remain automated.

Be precise about the boundary:

* **Human approval** - A person approves a specific release; a deterministic pipeline can then deploy the approved artifact.
* **Human-only execution** - A person performs the action. An approval elsewhere does not give the agent permission to publish, merge or send on their behalf.

For each reserved step, record **Human only**, the responsible role, a link to the enforcing control, and completion evidence such as the approval record, merge commit, published version or send receipt. For secret rotation, retain audit metadata, never secret values.

| Step (example data) | Human owner | Enforcing control | Completion evidence |
| --- | --- | --- | --- |
| Approve Northwind 2.4 for production | Release manager | Production environment requires a human reviewer; agent cannot approve or bypass | Approval record linked to the reviewed commit |

A [deployment plan](/do-you-have-a-deployment-plan) explains deployment and recovery; [gated deployments](/use-gated-deployments) cover deployment approval. Extend [human oversight of cloud agents](/cloud-ai-agents) to release actions outside the pipeline.

## Enforce the boundary outside the agent

Use a separate agent identity without the human owner's credentials, browser session, reviewer membership or administrative access. [Shared agent settings](/shared-ai-agent-settings) add local safeguards; the destination service must also reject unauthorised actions through its API or CLI.

* **Production approval** - Configure a [GitHub environment](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments) with human required reviewers, prevent self-review and disable administrator bypass. The deployment job must reference that environment. Keep production credentials behind the gate and remove alternative deployment credentials from the agent. In [Azure DevOps, use approvals and checks](https://learn.microsoft.com/en-us/azure/devops/pipelines/process/approvals?view=azure-devops) on the environment or service connection. Resource owners manage these checks outside pipeline YAML; keep the agent out of resource administration and approver roles.
* **Release merge** - Require PR review and restrict who can push or merge to the release branch to the human release team. Required reviews alone can still allow an agent to merge after approval. Apply [branch protection](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches), exclude agent identities from bypass access, and check auto-merge or merge-queue paths against the same boundary.
* **Package publishing** - Restrict publishing to designated people when execution is human only. Check inherited repository/workflow access and tokens. [GitHub Packages access controls](https://docs.github.com/en/packages/learn-github-packages/configuring-a-packages-access-control-and-visibility) distinguish read, write and admin roles; independent permissions depend on the registry. A deployment gate does not protect a separate publish job or registry token.
* **Secret rotation and announcements** - Give secret-management permissions to the operations role and customer-send permissions to the communications role. Give the agent only the access it needs to prepare instructions or drafts. Review connector permissions and shared sessions too.

Require human review for changes to release workflows and permission settings. An agent that can remove the gate or grant itself the missing role can cross the boundary. Keep any emergency access separate, human-controlled and audited.

## Tell the agent where to hand over

Link from your [AGENTS.md instructions](/write-agents-md) to the release checklist so both documents describe the same boundary. For example:

## Verify the boundary before relying on it

* **Test without production effects** - In a disposable project with equivalent controls, use the agent's actual identity to attempt each reserved operation through the UI and API or CLI. Expect a permission denial or a pending human approval, with no external action completed.
* **Check the permitted path** - Confirm the human owner can complete their step and the pipeline deploys only the reviewed commit or artifact. Record the result against the checklist.
* **Recheck after access changes** - Review tokens, inherited roles, workflow changes and bypass permissions. Preserve the approval and action records with the release evidence.

The boundary works when the agent can prepare the release, yet cannot approve or perform a reserved action using any credentials available to it.
