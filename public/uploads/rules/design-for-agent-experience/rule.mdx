Most apps are built for people. Good user interfaces and user experience (UX) help them find features and complete tasks.

AI agents use these apps too. Navigating pop-up logins and multi-step wizards through screenshots takes extra time and tokens, and can leave an unattended task stuck.

Agent experience (AX) is the experience of an agent using your product. Give agents a front door - a CLI, an MCP server, or WebMCP tools - so they can complete tasks through explicit operations and structured data.

<endIntro />

## What is agent experience (AX)?

Designing for AX means making your product easy for an AI agent to discover and use reliably. Command names, tool descriptions, schemas and error messages become its interface.

* **Reliable tools keep tasks moving** - An unexpected human-only step can block an unattended agent
* **Fewer screenshot-and-guess loops** - A structured call can replace a sequence of clicks
* **Clearer permissions** - A named tool with a schema is easier to approve than "click anything on the page"

## How is AX different from UX?

People use visual cues and shared context to navigate an app. Agents can interpret screens and infer meaning too, but explicit inputs, discoverable operations and structured results reduce guesswork.

* **Make inputs explicit** - A person may understand an unlabeled icon or "a couple of days". Give an agent named operations and defined units
* **Make operations discoverable** - A person browses menus. Let an agent list commands, tools and schemas, with documentation explaining their use
* **Make errors actionable** - A person may call support after "Something went wrong". An agent needs a stable error code and a clear next step
* **Support unattended use** - A person can answer a pop-up. An unattended agent needs preconfigured access or a clear way to report that human input is required

## Which AX surface should you build?

Pick by where the agent runs. The three surfaces complement each other, so many products offer more than one.

| Surface | Best for | Where it runs | Maturity |
| --- | --- | --- | --- |
| **CLI** | Dev tools and anything scriptable | The agent's shell | Stable - agents already write shell commands well |
| **MCP server** | Exposing your system or data to any agent | Your server or a local process | Established - open standard with broad client support |
| **WebMCP** | Actions inside the user's open browser tab | The user's browser | Early - draft spec, browser origin trials |

### CLI

A CLI can run locally without hosting a tool server, and shell-based agents can call it directly. Make it agent-friendly:

* **Never prompt** - Take input from flags and environment variables, not interactive questions
* **Output structured data** - Offer `--json` or similar, with an explicit empty result when nothing matches
* **Fail clearly** - Return meaningful exit codes, and reject unknown flags instead of ignoring them

#### Give CLI errors a stable contract

For commands that return a single result, document a machine-readable mode that writes one JSON document to stdout, including on failure. Use stable error codes for programmatic decisions, readable messages for explanation and a non-zero exit status on failure. Send progress and diagnostics to stderr so callers can parse stdout directly.

For example, a fictional Northwind export command rejects an invalid date with exit status 2 and this JSON on stdout. The exit value and response shape are specific to Northwind:

```json
{
  "ok": false,
  "data": null,
  "error": {
    "code": "INVALID_DATE",
    "message": "The --since date is invalid.",
    "hint": "Use a real date in YYYY-MM-DD format."
  }
}
```

**Figure: The stable code drives the caller's decision; the message and hint explain it**

Every outcome keeps the same shape, so a caller can tell an empty result from a failure without parsing prose:

| Outcome | Exit status | `ok` | `data` | `error` |
| --- | --- | --- | --- | --- |
| Rows found | 0 | `true` | `[...]` | `null` |
| No rows match | 0 | `true` | `[]` | `null` |
| Invalid date | 2 | `false` | `null` | `{"code": "INVALID_DATE", ...}` |

Document error codes and compatibility guarantees. Callers should:

* **Read the streams separately** - Parse stdout and treat stderr as diagnostics
* **Stop safely when unsure** - Unknown codes, missing or malformed output, or JSON that disagrees with the exit status all mean stop
* **Treat hints as advice** - Never execute a hint as a command

Test success, empty results, invalid flags, missing credentials, service errors and logging-enabled runs. Preserve parseable output and consistent exit status in each case, and redact secrets from both streams. Streaming commands need their own documented framing.

### MCP server

Use an MCP server to expose your system through a standard tool interface, locally or remotely. Tool names, descriptions and schemas help agents choose the right operation and supply valid inputs.

See [Do you have an MCP server to let AI agents plug into your app?](/mcp-server) for how to build one.

### WebMCP

WebMCP lets a web page register JavaScript tools that an in-browser agent can call, using `document.modelContext.registerTool()`. The agent reuses the user's session instead of re-authenticating.

## What makes good AX, whichever surface you pick?

* **Auth that fits the workflow** - For unattended tasks, configure scoped tokens or service accounts in advance. In a browser, use the user's authorized session
* **Errors that explain the fix** - Say what went wrong and what to try next
* **Descriptions written for agents** - Say what a tool does, what it needs, and what it returns
