A webhook sends data to a URL supplied by another organisation. A mistyped URL or compromised receiver can expose everything in the payload. An unsigned request also lets an attacker impersonate your service and trigger actions such as shipping an order.

When designing a webhook API, **send a small, signed notification containing IDs**, then let the receiver fetch details through an authenticated API. This limits what leaves your system and keeps access checks on the data read.

<endIntro />

## Keep customer details behind the API

Northwind notifies a delivery partner that order `123` has shipped. Both examples below use **example data**.

```json
{
  "eventType": "order.shipped",
  "orderId": "123",
  "customer": { "name": "Example Customer", "email": "customer@example.com" },
  "total": 4180.00,
  "deliveryNotes": "Leave at the example reception desk"
}
```

```json
{
  "eventType": "order.shipped",
  "occurredAt": "2026-11-06T00:00:00Z",
  "subject": { "orderId": "123" }
}
```

Northwind signs this body and the delivery metadata before posting to the same endpoint. The partner verifies it, then requests `https://api.example.com/orders/123` using its own API credential. The API checks that the partner can read this order before returning customer details.
  </>}

The event type, time and ID still reveal information. Minimise them too when their presence is sensitive. A signature proves integrity and possession of the signing key; it does not encrypt the payload. Use HTTPS.

Thin payloads add an API call and make processing depend on API availability. [Stripe's thin and snapshot event comparison](https://docs.stripe.com/events/how-events-work#event-formats) illustrates this trade-off. Use a configured API base URL and validate the resource ID; do not send an API credential to a URL supplied in the webhook body.

## Verify the exact bytes before processing

Use the sender's verification library and signing scheme. For a new API using the symmetric [Standard Webhooks signature scheme](https://github.com/standard-webhooks/standard-webhooks/blob/main/spec/standard-webhooks.md#signature-scheme), compute HMAC-SHA256 over the event ID, a dot, the attempt timestamp, another dot, and the **raw request body bytes**. Its headers are `webhook-id`, `webhook-timestamp` and `webhook-signature`. The signature uses the `v1,` prefix and a Base64-encoded MAC.

Verify with a constant-time comparison and reject attempt timestamps outside a short past/future tolerance. Never parse JSON and serialise it again to verify: even a whitespace change alters the signature. Keep server clocks synchronised. A valid signature within the tolerance can still be replayed, so deduplication is also required.

For Node.js, install `standardwebhooks` and save this verification helper as `verify.mjs`. It accepts a raw `Buffer` containing UTF-8 JSON and headers from the request; load `signingSecret` from trusted configuration. With Express, use `express.raw({ type: "application/json" })` on this route **before** any JSON body parser, and configure a request size limit.

```javascript
import { Webhook } from "standardwebhooks";

export function verifyDelivery(rawBody, headers, signingSecret) {
  if (!Buffer.isBuffer(rawBody)) {
    throw new TypeError("Capture the body before JSON parsing");
  }

  // Reject invalid UTF-8; pass the original bytes to the verifier.
  new TextDecoder("utf-8", { fatal: true }).decode(rawBody);
  return new Webhook(signingSecret).verify(rawBody, headers);
}
```

The [Standard Webhooks JavaScript library](https://github.com/standard-webhooks/standard-webhooks/tree/main/libraries/javascript) checks the MAC in constant time and rejects timestamps more than five minutes old or ahead. Catch verification errors at the HTTP boundary, return a failure response, and perform no business action. This helper verifies authenticity and freshness only; schema checks and durable deduplication remain application responsibilities.

**Example data:** `whsec_EXAMPLE_ONLY_do_not_use` is an intentionally invalid placeholder, not a usable signing key. For this scheme, provision a random endpoint-specific key and share its `whsec_`-prefixed Base64 encoding securely. Never put it in a payload, callback URL or source control; see [how to store secrets securely](/store-your-secrets-securely).

Do not reuse this helper for other protocols. [Stripe signs a timestamp and the raw body](https://docs.stripe.com/webhooks#verify-signature) using its own header format. [GitHub signs the body](https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries) with `X-Hub-Signature-256`; it does not use this signed timestamp scheme. Follow each provider's replay controls, including [GitHub's delivery ID guidance](https://docs.github.com/en/webhooks/using-webhooks/best-practices-for-using-webhooks#use-the-x-github-delivery-header).

## Make delivery and retries safe

* **Send after commit from an outbox.** Store the notification in the same transaction as the order change, then deliver it after commit. This prevents announcing an order change that rolls back. See [the Transactional Outbox pattern](/use-transactional-outbox-pattern) for dispatch and retry mechanics.
* **Keep the event ID across retries.** For Standard Webhooks, reuse `webhook-id` while refreshing the attempt timestamp and signature. The event's `occurredAt` stays unchanged.
* **Persist before acknowledging.** After verification and schema checks, atomically insert a durable inbox job with a unique key scoped to the sender/subscription and event ID. Return `2xx` once that job is durable, including for a known duplicate. If persistence fails, return a failure so the sender can retry. Keep deduplication records for the supported retry and manual-redelivery period, not just the signature tolerance.
* **Make processing idempotent.** A worker can crash after an external action but before marking its inbox job complete. Use the event ID as an idempotency key where the downstream system supports it. Retry temporary API-fetch failures with backoff, and alert after a bounded retry policy is exhausted.
* **Check authorisation at delivery and read time.** Do not deliver events to a subscription that has lost access to the subject. The follow-up API read must enforce the receiver's current permissions too.

For a planned secret rotation, temporarily sign with both old and new keys while receivers switch, then retire the old key. Standard Webhooks supports multiple signatures in one header. If a key is compromised, revoke it promptly and coordinate replacement; an overlap that still accepts it also accepts forged deliveries.

## Validate callback URLs and choose exceptions deliberately

A callback URL can make your sender request an internal service: a server-side request forgery (SSRF) attack. Require HTTPS, disable redirects, and block loopback, private, link-local and other non-public destinations for both IPv4 and IPv6. Validate at registration and each delivery attempt, then ensure the HTTP client connects only to the addresses you checked so DNS rebinding cannot bypass the check. Add network egress restrictions; follow the [OWASP SSRF prevention guidance](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html).

Choose a fuller payload when a documented requirement outweighs the extra disclosure: for example, the receiver needs a point-in-time snapshot or cannot call your API. A later resource fetch returns current state, which may have changed or been deleted; use an authorised event-history API or a minimal snapshot when that distinction matters. Include only approved fields, and retain signing, replay protection and delivery safeguards.

Before release, test a valid delivery, a changed body, an expired or future timestamp, and a duplicate delivery. Success means valid events reach the durable inbox, invalid requests cause no business action, retries cause one business outcome, and revoking API access blocks the details fetch.
