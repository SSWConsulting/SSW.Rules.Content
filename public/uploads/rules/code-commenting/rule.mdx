Comments can become stale while the code moves on, leaving maintainers to work out which version to trust. Before adding a comment, try clearer names, simpler code or targeted tests.

Keep comments that explain why the code must work this way. Remove those that merely repeat what it does or narrate the latest edit, including AI-written change notes.

<endIntro />

## Prefer clearer code

Comments add text for maintainers to understand. Review them during refactoring: prose can become stale and cannot enforce the behaviour it describes. Before adding an explanation:

* Give the class, function, parameter, variable or test a clearer, more descriptive name
* Rewrite cryptic code in simpler terms; keep necessary optimisations and explain any non-obvious constraints
* Add targeted tests to document and check the behaviour
* Split large methods or classes into smaller ones with descriptive names, or group related parameters in a Parameter Object
* Pair with someone else when you cannot find a clear approach

## Apply the one-year test

When reviewing a comment, ask: **would this comment still earn its place a year from now**, with the change long forgotten? Keep context that a future maintainer needs but cannot infer from the code. Remove narration of the change that produced it.

The [comments section of Google's code review guidance](https://google.github.io/eng-practices/review/reviewer/looking-for.html#comments) makes the same distinction between necessary reasoning and repetition of visible code.

### Keep the lasting constraint

Explain hidden constraints, sentinel values or necessary workarounds. Aim for one or two lines beside the relevant code, and link to the source of an idea or a longer explanation when needed. For a workaround, follow the guidance on [explanatory notes for non-standard code](/leave-explanatory-notes-for-non-standard-code).

In this Northwind example, `Orders.Source` stores numeric values, and older rows use 0 for an unset source. Renumbering the enum would make existing rows mean something different. Both versions below behave identically; only the comments change.

```csharp
public enum OrderSource
{
    // Renamed from LegacyChannel in the March refactor. Kept the same numbers
    // so the refactor did not need a data migration.
    Unknown = 0,
    Workflow = 1,
    Import = 2,
    Api = 3,
}
```

**❌ Figure: The refactor history omits the storage column and the meaning of the zero value**

```csharp
public enum OrderSource
{
    // Older Orders.Source rows use 0 for an unset source.
    // These numbers are stored in Orders.Source; renumbering misreads existing rows.
    Unknown = 0,
    Workflow = 1,
    Import = 2,
    Api = 3,
}
```

**✅ Figure: The comment explains the legacy zero value and the data corruption that renumbering would cause**

The explicit values are part of this example's storage contract, not a requirement for every enum. See the [C# enum reference](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/builtin-types/enum) for numeric values and zero defaults.

### Remove change narration

In AI-written code, check for comments such as `// Added null check` or `// Changed to use X`. These describe an edit rather than a lasting reason. The same test applies to human-written comments.

In this Northwind example, the function returns the shipping country, or null if no order is selected. Removing the narration preserves that behaviour and leaves less text to maintain.

```typescript
function getShipCountry(order: { shipCountry: string } | null): string | null {
  // Added null check
  if (order === null) {
    return null;
  }

  // Changed to use shipCountry
  return order.shipCountry;
}
```

**❌ Figure: The comments repeat the visible null check and property access without explaining a constraint**

```typescript
function getShipCountry(order: { shipCountry: string } | null): string | null {
  if (order === null) {
    return null;
  }

  return order.shipCountry;
}
```

**✅ Figure: The same function communicates its behaviour through its name, types and code**

Put completed-work references and "renamed from/changed from" narration in [commit history](/comment-when-your-code-is-updated). Keep broader decisions in [PR descriptions or decision records](/keep-the-why-from-ai-assisted-development). A link that explains an ongoing constraint can still belong beside the code.

To prevent this noise in later tasks, add a standing instruction to the [agent's project instructions](/write-agents-md):

```markdown
Do not add comments that narrate edits. Keep necessary explanations of lasting
constraints beside the code, and put change history in commits or PR descriptions.
```

**Figure: A project instruction states which comments to omit and which explanations to preserve**

## Handle documentation, TODOs and commented-out code

Account for these special cases during review:

* **API documentation:** Describe purpose, usage and behaviour rather than repeating a member's name. [C# XML documentation comments](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/xmldoc/) support generated API documentation, including for public NuGet libraries
* **Legal notices:** Keep required copyright and licence notices
* **Complex logic:** A regular expression or algorithm can need an explanation of how it works when simpler code cannot make it clear
* **TODOs:** Resolve small reminders while working. Before merging unfinished work, [track the TODO in a work item and link it](/todo-tasks); delete the TODO when the work is done
* **Unused code:** Remove abandoned feature implementations kept in comments "just in case"; source control preserves them. Disabled debug or trace statements are a separate case covered by the [debugging comments guidance](/what-to-do-with-comments-and-debug-print-statements)

Before approving a change, read the remaining comments alongside the affected code and update any explanation that no longer matches it.
