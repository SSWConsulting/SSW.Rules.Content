Comments can become stale while the code moves on, leaving maintainers to work out which version to trust. Before adding a comment, try clearer names, simpler code or targeted tests.

Keep comments that explain why the code must work this way. Remove those that merely repeat what it does.

<endIntro />

## What are the downsides of comments?

1. Refactoring code does not guarantee that its comments stay accurate; review them alongside the code
2. A prose comment cannot enforce the behaviour it describes; use tests for behaviour you can check
3. Unless carefully chosen, comments add to the reader's workload: they must understand both the code and the comments

## What are the alternatives to comments?

1. Give the element (class, function, parameter, variable, test etc.) a clearer, more descriptive name
2. Rewrite cryptic code in simpler terms; keep necessary optimisations and explain any non-obvious constraints
3. Add targeted unit tests to document the behaviour
4. Use established solutions to common code smells, e.g.:
   * Split large methods/classes into smaller ones with descriptive names
   * For a method with many parameters, group related parameters in a Parameter Object
   * Pair with someone else to find a clearer approach

## What are some bad comments?

1. Comments that explain the "what" or "how" by restating the code in plain language
2. Boilerplate documentation that repeats a member's name without explaining its purpose or use
3. Commented-out code saved for later — that's what source control is for
4. TODO comments that linger — resolve small reminders while working; before merging unfinished work, [track the TODO in a work item and link it](/todo-tasks), then delete the TODO when the work is done

## What are some good comments?

1. Comments that explain why the code works this way
2. Comments that link to the external source of an idea or piece of code
3. Comments that explain a non-obvious constraint; keep change history and links to completed Bugs/PBIs in the commit message or PR description
4. Documentation comments that explain how to use an API, such as a public NuGet library; [C# XML documentation comments](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/xmldoc/) support generated API documentation
5. Comments that explain a necessary workaround and link to an authoritative source for the constraint; follow the guidance on [explanatory notes for non-standard code](/leave-explanatory-notes-for-non-standard-code)

This distinction also appears in [Google's code review guidance on comments](https://google.github.io/eng-practices/review/reviewer/looking-for.html#comments): explain reasoning the code cannot convey. Complex algorithms or regular expressions can still need an explanation of how they work.

## The one-year test

A good comment explains something that stays true and is not obvious from the code: what a sentinel value means, an invariant, or why a value must never change. A bad comment narrates the change that produced the current code or restates what is on the line. Once the change settles, that narration becomes stale clutter.

When reviewing AI-written code, look for comments that narrate the diff, such as `// Added null check` or `// Changed to use X`. Ask: **would this comment still earn its place a year from now**, with the change long forgotten?

Use this checklist when reviewing comments:

* **Default to no comment** - Improve names or structure first
* **Keep explanatory comments short** - Aim for one or two lines for a hidden invariant or a non-obvious reason; keep essential context beside the code and link to longer rationale
* **Keep change history out of code** - Put "renamed from/changed from" narration and completed-work references in the commit message or PR description. Keep links needed to explain an ongoing constraint or track unfinished work
* **Keep required documentation** - Public API docs and legal notices serve a different purpose

### Keep the lasting constraint

In this Northwind example, `Orders.Source` stores numeric values, and older rows use 0 for an unset source. Renumbering the enum would make existing rows mean something different. Both versions below behave identically; only the comments change.

```csharp
public enum OrderSource
{
    // Renamed from LegacyChannel in the March refactor. Kept the same numbers
    // so the refactor did not need a data migration.
    Unknown = 0,
    Workflow = 1,
    Import = 2,
    Api = 3,
}
```

**❌ Figure: The refactor history leaves a maintainer guessing why the numeric values must stay fixed**

```csharp
public enum OrderSource
{
    // Older Orders.Source rows use 0 for an unset source.
    // These numbers are stored in Orders.Source; renumbering misreads existing rows.
    Unknown = 0,
    Workflow = 1,
    Import = 2,
    Api = 3,
}
```

**✅ Figure: The comment explains the legacy zero value and the data corruption that renumbering would cause**

The explicit values are part of this example's storage contract, not a requirement for every enum. See the [C# enum reference](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/builtin-types/enum) for numeric values and zero defaults.

### Remove change narration

In this Northwind example, the function returns the shipping country, or null if no order is selected. Removing the narration preserves that behaviour and leaves less text to maintain.

```typescript
function getShipCountry(order: { shipCountry: string } | null): string | null {
  // Added null check
  if (order === null) {
    return null;
  }

  // Changed to use shipCountry
  return order.shipCountry;
}
```

**❌ Figure: The comments repeat the visible null check and property access without explaining a constraint**

```typescript
function getShipCountry(order: { shipCountry: string } | null): string | null {
  if (order === null) {
    return null;
  }

  return order.shipCountry;
}
```

**✅ Figure: The same function communicates its behaviour through its name, types and code**

Before approving, check that each remaining comment adds context the code cannot express, and update any comment affected by the change. Keep broader decisions in [PR descriptions or decision records](/keep-the-why-from-ai-assisted-development).
