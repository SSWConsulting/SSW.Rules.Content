Comments can become stale while the code moves on, leaving readers to work out which version to trust. There is almost always a better alternative: clearer names, simpler code or targeted tests.

Keep comments that explain why the code must work this way. Remove those that merely repeat what it does.

<endIntro />

[Chapter 4: Comments, Clean Code](https://www.amazon.ca/Clean-Code-Handbook-Software-Craftsmanship-ebook/dp/B001GSTOAM) explores when comments help and when clearer code is the better choice.

## What are the downsides of comments?

1. Comments aren't automatically updated during refactoring, so they quickly become stale
2. Compilers generally ignore comments, so they cannot enforce the behaviour a comment describes
3. Unless carefully chosen, comments add to the reader's workload: they must understand both the code and the comments

## What are the alternatives to comments?

1. Give the element (class, function, parameter, variable, test etc.) a clearer, more descriptive name
2. Rewrite cryptic code in simpler terms; leave optimisation to the runtime where possible
3. Add targeted unit tests to document the behaviour
4. Use established solutions to common code smells, e.g.:
   * Split large methods/classes into smaller ones with descriptive names
   * For a method with many parameters, group related parameters in a Parameter Object
   * Pair with someone else to find a clearer approach

## What are some **bad** comments?

1. Comments that explain the "what" or "how" by restating the code in plain language
2. Unnecessary documentation comments on non-public code
3. Commented-out code saved for later — that's what source control is for
4. TODO comments that linger — small ones are OK briefly, but anything over an hour or two becomes a work item; reference its ID in the TODO, then delete the TODO when the work is done

## What are some **good** comments?

1. Comments that explain why the code works this way
2. Comments that link to the external source of an idea or piece of code
3. Comments that explain a non-obvious constraint; keep change history and links to completed Bugs/PBIs in the commit message or PR description
4. Documentation comments for a public library, such as a NuGet package
5. Comments that explain a necessary workaround and link to an authoritative source for the constraint

## The one-year test

A good comment explains something that stays true and is not obvious from the code: what a sentinel value means, an invariant, or why a value must never change. A bad comment narrates the change that produced the current code or restates what is on the line. Once the change settles, that narration becomes stale clutter.

AI coding agents are especially prone to narrating the diff they just made. Review their comments with this test: would this comment still earn its place a year from now, with the change long forgotten?

Use this checklist when reviewing comments:

* **Default to no comment** - Improve names or structure first
* **Keep explanatory comments short** - Use one or two lines for a hidden invariant or a non-obvious reason; put longer rationale in an ADR or documentation
* **Keep change history out of code** - Put ticket numbers, PR links and "renamed from/changed from" narration in the commit message or PR description
* **Keep required documentation** - Public API docs and legal notices serve a different purpose

```csharp
public enum OrderSource
{
    // Renamed from LegacyChannel in the March refactor. Kept the same numbers
    // so the refactor did not need a data migration.
    Workflow = 1,
    Import = 2,
    Api = 3,
}
```

**❌ Figure: Bad example - The comment records the refactor instead of explaining the lasting constraint**

```csharp
public enum OrderSource
{
    // 0 means the source was never set. New code never writes it.
    // These values are persisted in Orders.Source, so never renumber them.
    Unknown = 0,
    Workflow = 1,
    Import = 2,
    Api = 3,
}
```

**✅ Figure: Good example - The comment explains what 0 means and why the values must never change**

> "A comment is an apology for not choosing a more clear name, or a more reasonable set of parameters, or for the failure to use explanatory variables and explanatory functions. Apologies for making the code unmaintainable, apologies for not using well-known algorithms, apologies for writing 'clever' code, apologies for not having a good version control system, apologies for not having finished the job of writing the code, or for leaving vulnerabilities or flaws in the code, apologies for hand-optimizing C code in ugly ways."
>
> — Uncle Bob (Robert Martin of 'Clean Code' fame)
