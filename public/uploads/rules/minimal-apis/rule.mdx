Controllers come with a lot of ceremony: a base class, routing attributes, action methods, and a class that groups unrelated endpoints together just because they share a URL prefix. Most of the time an endpoint just binds a request, calls a handler, and returns a result. The controller adds nothing to that.

Minimal APIs let you declare routes and handlers directly, with far less code. Microsoft now recommends them as the starting point for new ASP.NET Core APIs. If you want more structure, [FastEndpoints](https://fast-endpoints.com) builds on Minimal APIs and gives every endpoint its own class.

<endIntro />

```csharp
[ApiController]
[Route("[controller]")]
public class HelloWorldController : ControllerBase
{
    [HttpGet]
    public IActionResult Get()
    {
        return Ok("Hello World!");
    }
}
```

**❌ Figure: Bad example - 9 lines of code for a simple endpoint**

```csharp
app.MapGet("/", () => "Hello World!");
```

**✅ Figure: Good example - 1 line of code for a simple endpoint**

## Why Minimal APIs?

* **Less code** - No base classes, attributes or action methods to write
* **Performance** - Lower overhead per request than MVC controllers
* **Native AOT** - Minimal APIs support Native AOT publishing; controllers don't
* **Feature-focused** - Each endpoint can live next to the rest of its feature, which suits [Vertical Slice Architecture](/vertical-slice-architecture)
* **Easier testing** - Handlers are plain methods that you can call directly
* **Familiar** - A developer experience similar to Node.js frameworks like Express

Read [Choose between controller-based APIs and Minimal APIs](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/apis?WT.mc_id=DT-MVP-33518) on Microsoft Learn for the full comparison.

## Keep endpoints organized as the API grows

The usual objection to Minimal APIs is that `Program.cs` turns into one huge file. That only happens if you put every endpoint there. Instead:

* **Use route groups** - `MapGroup` shares a prefix, tags, authorization and filters across related endpoints
* **Return `TypedResults`** - The return type documents every possible response, so OpenAPI metadata is generated for you and unit tests can check the result type
* **Map each feature in its own file** - An extension method per feature keeps `Program.cs` to a few lines of wiring

```csharp
public static class TodoEndpoints
{
    public static void MapTodoEndpoints(this IEndpointRouteBuilder app)
    {
        var group = app.MapGroup("/api/todos")
            .WithTags("Todos")
            .RequireAuthorization();

        group.MapGet("/{id:int}", GetTodo);
    }

    private static async Task<Results<Ok<TodoResponse>, NotFound>> GetTodo(
        int id,
        AppDbContext db,
        CancellationToken ct)
    {
        var todo = await db.Todos.FindAsync([id], ct);

        return todo is null
            ? TypedResults.NotFound()
            : TypedResults.Ok(new TodoResponse(todo.Id, todo.Title));
    }
}
```

**✅ Figure: Good example - A route group, typed results, and a feature file that `Program.cs` wires up with `app.MapTodoEndpoints()`**

From .NET 10, Minimal APIs also validate requests for you. Call `builder.Services.AddValidation()` and data annotations on your request types are checked before the handler runs, with a `400 Bad Request` returned when they fail. See the [Minimal APIs quick reference](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/minimal-apis?WT.mc_id=DT-MVP-33518) for details.

## Consider FastEndpoints for more structure

FastEndpoints is an open source (MIT) library that sits on top of Minimal APIs. Each endpoint is a class with a request DTO, a handler and a response DTO, following the REPR (Request-Endpoint-Response) pattern. Endpoints are discovered automatically, so there is no mapping code to maintain.

```csharp
public sealed class GetTodoRequest
{
    public int Id { get; set; }
}

public sealed record TodoResponse(int Id, string Title);

public class GetTodoEndpoint(AppDbContext db) : Endpoint<GetTodoRequest, TodoResponse>
{
    public override void Configure()
    {
        Get("/api/todos/{Id}");
    }

    public override async Task HandleAsync(GetTodoRequest req, CancellationToken ct)
    {
        var todo = await db.Todos.FindAsync([req.Id], ct);

        if (todo is null)
        {
            await Send.NotFoundAsync(ct);
            return;
        }

        await Send.OkAsync(new TodoResponse(todo.Id, todo.Title), ct);
    }
}
```

**✅ Figure: Good example - A FastEndpoints endpoint with its own request and response DTOs**

The class-per-endpoint shape pushes teams towards [unique DTOs per endpoint](/unique-dtos-per-endpoint) and one folder per feature. FastEndpoints also includes FluentValidation, pre and post processors, an in-process event bus, and strongly typed integration testing helpers.

### Which one should you choose?

* **Minimal APIs** - The default. They are first-party, have no extra dependency, and are where Microsoft adds new features first
* **FastEndpoints** - When you want the REPR structure enforced across a larger team, or you would otherwise rebuild its features yourself. The trade-off is a third-party dependency and its own conventions to learn

Either way, keep each endpoint thin. It should bind the request, call the business logic (e.g. a [mediator handler](/use-the-mediator-pattern-with-cqrs)), and map the result.

## When are controllers still the right choice?

Controllers still provide a few features that Minimal APIs don't have out of the box:

* OData
* Custom model binders (`IModelBinderProvider`, `IModelBinder`)
* Custom model validators (`IModelValidator`)
* Application parts and the application model

If an existing app relies on these, keep its controllers. You can add Minimal API endpoints to the same app and move existing endpoints across gradually.
