A single architecture diagram that tries to show everything ends up serving no one. A stakeholder gets lost in queues and databases, and a developer can't find the detail they need among the external systems and user types. Worse, every team invents its own boxes and arrows, so each new diagram needs a legend and an explanation.

<endIntro />

The [C4 model](https://c4model.com/) solves this the way an online map does. You start zoomed out to see the whole country, then zoom in to see a city, then a street. Each level adds detail to the one above it, and each element on one level expands into the diagram below it.

## The 4 levels of zoom

Each level answers a different question for a different audience:

| Level | Shows | Answers | Audience |
| --- | --- | --- | --- |
| 1. System Context | Your system as one box, plus the people and external systems it interacts with | What is this system and who uses it? | Everyone, including non-technical stakeholders |
| 2. Container | The applications and data stores inside your system and how they communicate | How is the system built and deployed? | Developers, architects, and operations |
| 3. Component | The major building blocks inside one container and their responsibilities | How does this container work inside? | Developers working on that container |
| 4. Code | Classes and interfaces inside one component | How is this component implemented? | Rarely needed |

### Level 1 - System Context

The big picture. It shows the people (in specific roles, e.g. Customer or Warehouse Staff) who use the system, and the external systems it depends on (e.g. a payment gateway or an email service). There is very little detail here, which is the point: anyone can understand it.

### Level 2 - Container

Usually the most useful level. A container is anything that runs code or stores data, e.g. a single page application, an API, a serverless function, a database, blob storage, or a message bus. This is the level most people mean when they ask for "the architecture diagram".

**Note:** A C4 container is not a Docker container. A Docker container might host a C4 container, but the terms mean different things.

### Level 3 - Component

The major building blocks inside a single container, e.g. controllers, services, or a data access layer. This is a conceptual view, not a 1:1 map of every class, so keep it focused on the parts that matter.

### Level 4 - Code

A 1:1 map of the classes in a component. It's rarely worth drawing by hand, because the code already tells the same story and the diagram goes stale on the next refactor. If you need it, generate it from the code. See [Do you generate dependency graphs?](/generate-dependency-graphs)

## Why levels of zoom matter

* **Each audience gets the right amount of detail** - Show the client the System Context diagram, and give a new developer the Container diagram
* **Diagrams stay readable** - Each level stays small enough to understand at a glance
* **Diagrams change less often** - Higher levels rarely change, so they don't go stale when a class or service is renamed
* **Navigation is consistent** - People always know where to look for more detail: zoom in one level
* **Everyone speaks the same language** - "Container" and "Component" mean the same thing on every project, so diagrams need less explanation

## Draw only the levels you need

Most projects only need the first 2 levels. Add a Component diagram for containers that are complex enough to need one, and skip the Code level.

C4 also has supplementary diagrams for specific needs:

* **System Landscape** - Every system in the organization and how they relate
* **Deployment** - How containers map to infrastructure, e.g. resource groups, load balancers, and CDNs
* **Dynamic** - How elements collaborate for one feature or use case, similar to a sequence diagram

## Model once, draw many diagrams

C4 separates **modelling** (describing the people, systems, containers, components, and their relationships) from **diagramming** (drawing pictures of that model). When you keep a single model, every diagram is a view of it, so renaming a container updates every diagram that shows it.

The C4 model is notation-independent, so you can use any tool:

* **draw.io** - Includes a C4 shape library. Put each level on its own page in the same `.drawio` file. See [Do you have an architecture diagram?](/architecture-diagram) for draw.io tips
* **[Structurizr](https://structurizr.com/)** - Built by the creator of C4. You write the model once in a text DSL, and Structurizr generates every view from it. It can also hold documentation and [Architectural Decision Records](/architectural-decision-records) alongside the model
* **Mermaid and PlantUML** - Both support C4 syntax, which works well when you already use them for other diagrams. See [Do you use Mermaid diagrams?](/use-mermaid-diagrams)

```text
model {
    customer = person "Customer"
    emailSystem = softwareSystem "Email System" "Sends order emails" "External"

    ecommerce = softwareSystem "E-commerce System" {
        storeSpa = container "Store SPA" "Lets customers buy products" "React"
        api = container "API" "Handles orders and stock" "ASP.NET Core"
        database = container "Database" "Stores products and orders" "SQL Server"
    }

    customer -> storeSpa "Places orders using"
    storeSpa -> api "Calls" "HTTPS"
    api -> database "Reads and writes" "EF Core"
    api -> emailSystem "Sends emails using" "SMTP"
}

views {
    systemContext ecommerce "Context" {
        include *
        autoLayout
    }

    container ecommerce "Container" {
        include *
        autoLayout
    }
}
```

**Figure: Good example - A Structurizr DSL model with 2 views generated from it. The Context and Container diagrams can never disagree**

Because these are text files, they live in the repo next to the code and get reviewed in the same pull request as the change they describe.
