Until recently, the only ways to change how a coding agent behaved were its instructions file (AGENTS.md, CLAUDE.md, etc) and, on most agents, shell-command hooks. If you wanted the agent to display additional information, or to stop doing something it kept doing, you waited for the vendor to ship it.

That has changed. Every major agent now has lifecycle hooks (**Claude Code**, **Codex**, **GitHub Copilot**, **Gemini CLI** and **Cursor**), Claude Code has a scriptable status line, and in October 2026 Anthropic shipped **mods**, TypeScript functions that run inside Claude Code and can rewrite what it does or draw new UI.

Most developers still run their agent stock. That is why people find out about their weekly limit when they hit it, don't know which models their plan includes, and keep re-typing the one rule in AGENTS.md the agent ignores. So what can you actually customize, and how far should you go?

<endIntro />

## What can you customize?

There are four layers. Each one up is more powerful and more work, so start at the bottom and stop as soon as the problem is solved.

| Layer            | What it is                                                                                        | Enforced?                                    | Reach for it when                                     |
| ---------------- | ------------------------------------------------------------------------------------------------- | -------------------------------------------- | ----------------------------------------------------- |
| **Instructions** | AGENTS.md, CLAUDE.md, scoped rule files                                                           | No - the model reads it and usually complies | Conventions, context, preferences                     |
| **Skills**       | Reusable prompts and scripts the agent loads on demand                                            | No                                           | Repeatable workflows - "do a PR review our way"       |
| **Hooks**        | Scripts or code that run at lifecycle points: before a tool call, after an edit, at session start | **Yes** - the agent can't skip them          | "Every time X, do Y" rules the agent keeps forgetting |
| **Mods**         | Code that runs inside the agent and can rewrite events or draw UI                                 | **Yes**                                      | The agent needs a feature it doesn't have             |

If a rule in AGENTS.md keeps getting ignored, it belongs in a hook. Instructions are advisory. Hooks run every time.

See [Do you use skills to standardize AI workflows?](/ai-agents-with-skills) for the skills layer.

## How do you see your usage limits?

You can't budget what you can't see. Every agent will tell you your model, how full the context window is and how much of your plan you've burned, but only if you ask. Put it somewhere that's visible 100% of the time.

In Claude Code, the status line is a shell script that receives the session as JSON on stdin: model, context window, cost and both rate-limit windows. You don't have to write it yourself:

```text
/statusline show the model, context % and my 5-hour and 7-day usage with reset times
```

That gives you something like:

```text
Fable | ctx 42% | 5h 61% (resets 17:00) | 7d 83% (resets Mon 09:00)
```

Now the numbers drive the decision:

| What you see                               | What to do                                                                                |
| ------------------------------------------ | ----------------------------------------------------------------------------------------- |
| 7-day usage low, 5-hour window fresh       | Go nuts. Parallel subagents, the big refactor, the premium model                          |
| 5-hour window above 80%, resets in an hour | Finish the current task, don't start the next big one                                     |
| Context above 70%                          | Consider `/compact` or `/clear`, as quality may drop and every prompt gets more expensive |

A few commands worth knowing even without a status line:

* `/usage` - plan usage bars, plus a breakdown of which skills, subagents, plugins and MCP servers are eating your budget
* `/context` - what is actually in the context window right now
* `/model` - which models your plan gives you. Check it. Plenty of developers are on the default model without knowing a stronger one is a keystroke away

The other agents expose the same numbers, with less freedom in how you show them:

| Agent              | How you get usage on screen                                                                                    | Limits                                                                                                                    |
| ------------------ | -------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| Claude Code        | `/statusline` runs any script you like, with model, context, cost and both rate-limit windows on stdin         | None worth noting                                                                                                         |
| OpenAI Codex       | `/statusline` picks from a fixed list of items, including `context-used`, `five-hour-limit` and `weekly-limit` | No custom scripts. Shows remaining %, no reset times                                                                      |
| GitHub Copilot CLI | `/statusline` runs a custom command, same shape as Claude's                                                    | Its stdin payload isn't documented, and community status lines query quota themselves rather than reading it from Copilot |
| Cursor CLI         | `statusLine` command in `cli-config.json`, same shape as Claude's                                              | Replaces the native footer rather than adding to it, and carries no plan usage                                            |

### Status line or mod?

You may want your usage stats in the status line itself. Mods can't draw there: the status line's row isn't one of the components a mod can render, so a mod shows usage as a band above the prompt, a pinned line of its own under the prompt, or a toast. For the status line proper, use the `/statusline` script, or a tool like [goccc](https://github.com/backstabslash/goccc), which formats the same stdin data and adds cost history from your session logs. The two coexist, and the data is identical: a mod reads it from `$.session.usage()` and the `session.measure` event, the script reads it from stdin.

## How do you write a hook?

Every major agent has hooks, and they share one shape. Whatever the agent, a hook has five parts:

* **Trigger event** - when it runs: before a tool call, after an edit, at session start
* **stdin JSON** - what the agent hands you: the tool name and its arguments, the session, the working directory
* **Execution logic** - the one check or action the hook exists for
* **Deterministic exit code** - 0 lets the action through, 2 blocks it. There is no "maybe"
* **stderr** - the message the agent reads when you block it, so it can do something else instead

<boxEmbed
  style="greybox"
  body={<>
    A `PreToolUse` hook on `Bash` reads the command from stdin, matches `git push --force`, writes "Blocked: no force pushes on this repo" to stderr and exits 2. The agent sees the message and pushes a normal commit instead.
  </>}
  figurePrefix="good"
  figure="The rule in AGENTS.md that the agent ignored once a week now runs on every command"
/>

Three hooks worth having on every project:

* **Block the command you never want run** - force pushes, `rm -rf`, anything touching a production connection string
* **Run the formatter and tests after every edit** - a `PostToolUse` hook on `Edit|Write` so the agent sees failures immediately instead of you seeing them in the PR
* **Inject context at session start** - a `SessionStart` hook that returns the current branch, the ticket it belongs to and the sprint goal, so you stop pasting the same three lines into every prompt

Hooks can also shrink what the agent reads. A `PreToolUse` hook that rewrites `npm test` to `npm test | grep -A5 FAIL` turns a 10,000-line log into a few hundred tokens.

| Agent                                                                                                    | Where hooks live                           | Key events                                                                             | Org-level enforcement                                  |
| -------------------------------------------------------------------------------------------------------- | ------------------------------------------ | -------------------------------------------------------------------------------------- | ------------------------------------------------------ |
| [Claude Code](https://code.claude.com/docs/en/hooks)                                                     | `settings.json` (user, project or managed) | `PreToolUse`, `PostToolUse`, `PermissionRequest`, `SessionStart`, `Stop`, `PreCompact` | Managed policy settings                                |
| [OpenAI Codex](https://learn.chatgpt.com/docs/hooks)                                                     | `.codex/hooks.json` or `config.toml`       | `PreToolUse`, `PostToolUse`, `PermissionRequest`, `SubagentStart/Stop`, `Stop`         | Admin `requirements.toml`                              |
| [GitHub Copilot](https://docs.github.com/en/copilot/reference/copilot-cli-reference/cli-hooks-reference) | `.github/hooks/*.json`                     | `preToolUse`, `postToolUse`, `userPromptSubmitted`, `agentStop`, `preCompact`          | Policy directory, loaded before user and project hooks |
| [Gemini CLI](https://geminicli.com/docs/hooks/)                                                          | `settings.json`                            | `BeforeTool`, `AfterTool`, `BeforeModel`, `AfterModel`, `BeforeAgent`                  | Via extensions                                         |

## When do you need a mod?

Hooks can block and rewrite, but they can't add a feature or draw on the screen. Mods can, because they open up the Claude Code harness. A mod is a TypeScript function that Claude Code calls from inside its own process, on the same events hooks see, plus every part of the interface it draws. Your code can run before an event, after it, or instead of it. The built-in `/diff` command is now itself a mod.

<boxEmbed
  style="greybox"
  body={<>
    **Use case:** Every time Claude writes "Adam Cogan" in a reply, a mod rewrites the rendered message to "😎 The Big Boss". Ten lines of TypeScript on the `ui.render` event, hot-reloaded into the session without restarting Claude Code.
  </>}
  figurePrefix="good"
  figure="A mod changes what Claude Code draws, which no hook or skill can do"
/>

That same access is how you react to the usage numbers in your status line. The `session.measure` event fires after every turn and whenever a rate-limit window moves a point, so a toast at 80% of the weekly window is a few lines. Anthropic's samples show the range: `token-weather` charts your context window above the prompt after each turn, and `blast-radius` holds a risky shell command such as a force push and shows what it would change before you confirm.

You don't need to hand-write them. Ask Claude Code for a mod, and it writes the TypeScript, installs it and hot-reloads it in the session. Mods ship inside plugins, so you install and share them with `/plugin` like anything else.

Nobody else has an equivalent yet. The closest is [OpenCode](https://opencode.ai/docs/plugins/), whose TypeScript plugins can add tools and draw in the TUI. Codex, Copilot, Gemini and Cursor stop at hooks.

## Why treat hooks and mods as installed code?

A hook that can rewrite a tool call or auto-approve a permission is exactly what a malicious hook would do. Anthropic's own wording on mods: they "aren't sandboxed, and you should only install mods from sources you trust, the same way you'd install any code on your computer." One community scanner's September 2026 snapshot of 72 published mods found that 30 spawned processes, 14 reached the network, and about a third saw every prompt or tool call.

* **Read before you install** - a mod or hook from a marketplace is code running as you. Apply the same checks as [Do you verify the safety of AI skills before using them?](/verify-ai-skill-safety)
* **Prefer org-level enforcement over asking developers to behave** - Claude's `sec-default` mod on Team and Enterprise plans, Copilot's policy directory and Codex's `requirements.toml` all load ahead of anything a developer configures in a project
* **Put each customization in the right place** - personal ones in `CLAUDE.local.md` or `settings.local.json` (see [Do you keep personal Claude Code overrides in CLAUDE.local.md?](/claude-local-md)), team ones in the repo, org ones in managed settings (see [Do you centralize your team's AI workflows?](/centralize-ai-workflows))
