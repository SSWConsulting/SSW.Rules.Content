An [Azure Container Apps job](https://learn.microsoft.com/en-us/azure/container-apps/jobs) is a container that runs a task for a finite time and then stops. It starts manually, on a schedule, or when an event arrives.

Deploying a change to Azure just to see whether your job works is **slow, and every attempt costs a deployment ❌**

A job is just a container image, so Docker can run that same image on your machine with the same CPU and memory limits. You find a broken image, a missing setting or an out-of-memory crash in minutes, not after a deployment.

## ✅ Run the job in Docker, the way Azure runs it

On EagleEye, this is how we test changes to our Container Apps job. When a developer presses **Start Scan** in the local portal, the API starts the real job image in Docker, with the same limits as the job in Azure (2 vCPU and 4 GiB). The scan runs against real services, and the portal shows its progress as it does in Azure. A change to the job is checked in minutes.

Under the hood it is a normal `docker run`, with the job's limits:

```bash
docker run --rm --name orders-local --platform linux/amd64 \
  --cpus=2 --memory=4g --env-file ./staging.env \
  orders-job:local process-orders --since 2026-09-01
```

Put secrets in the env file (`chmod 600`), not in `-e` flags. Command-line arguments end up in your shell history and in `ps`.

## ✅ Why Docker is useful

* **Same image** - You test the build that ships, not your code running inside something else
* **Same limits** - `--cpus` and `--memory` apply the job's limits, and .NET sizes its threads and garbage collector to match
* **Real crashes** - .NET sees the memory limit and throws `OutOfMemoryException` at 75% of it, so a job that loads too much fails locally the way it fails in Azure
* **Real services** - Point it at your staging services, not fakes. [The Twelve-Factor App](https://12factor.net/dev-prod-parity) says to resist "the urge to use different backing services between development and production"
* **Same CPU architecture** - `--platform linux/amd64` runs the Intel image on an ARM laptop too. It is slower, because Docker emulates it

### ❌ What a local run can't tell you

Docker gets you much closer to Azure, but it is not Azure. A local run does not test:

* **Identity** - Locally the job signs in as you, not as its managed identity, so missing role assignments only show up in Azure
* **Key Vault references** - Locally the secrets come from your env file
* **Triggers** - Scheduled and event triggers do not fire. You start the job yourself
* **Speed** - Your laptop's CPU is not Azure's, so run times do not transfer

That means Docker should improve your inner loop, not replace a test in Azure.
