A nightly product-description job reports success, but some descriptions contain unsupported claims. Its preferred model times out, so a catch-all handler silently calls another model. Both return valid JSON. The saved rows contain no model details, leaving operators unable to identify the affected products.

**Make model changes explicit, tested and traceable.** A successful API call does not prove that a replacement meets the pipeline's quality or data-handling requirements. When no approved route succeeds, leave the item visibly failed or pending review.

## Check every layer that can change the model

Choose a model and version where supported, then run [evals](/run-evals-on-ai-features) before changing them. Inspect the application, SDK, gateway and deployment settings. A retry repeats a request; a model fallback changes the model used to fulfil it. Retrying the same deployment name does not guarantee the same model if a gateway routes it elsewhere or the deployment upgrades.

For example, [Microsoft Foundry model-version policies](https://learn.microsoft.com/en-us/azure/foundry/foundry-models/concepts/model-versions) can automatically upgrade Standard deployments. Review the policy for your deployment type and plan for [model retirements](/ai-model-retirements); pinning a version does not keep it available forever.

Record the following with each saved result, and retain attempt records for failures:

* Requested model or deployment, provider and routing-configuration revision
* Provider-reported model identifier and version, when exposed
* Prompt version, validation outcome and any fallback reason
* Job, item and request IDs that connect the result to its attempts

A deployment alias is not evidence of its resolved version. When response metadata is insufficient, use deployment or gateway records and record any remaining uncertainty. If an exact approved version is required and cannot be established, hold the item for review. Keep sensitive prompts, credentials and source documents out of routine logs.

## Retry for a reason, with a limit

Set a total attempt limit, a per-attempt timeout, an overall deadline and a token or cost budget. Include retries inside SDKs and gateways in those limits.

The [OpenAI Python SDK](https://developers.openai.com/api/reference/python#retries) and [Anthropic Python SDK](https://platform.claude.com/docs/en/cli-sdks-libraries/sdks/python#retries) document two automatic retries for certain connection and HTTP errors by default. Both expose `max_retries`; `0` disables these retries. These settings govern retries, not approval of another model. Check your installed SDK version and routing configuration separately.

| Failure | Action within the remaining budget |
| --- | --- |
| Transient timeout or throttling | Retry the approved route with backoff and jitter, respecting the provider's retry delay |
| Output stopped at its token limit | Reject the partial result; consider a larger output allowance on the same model, within its supported limits |
| Invalid schema or unsupported claim | Reject it; retry only when there is a specific, recoverable cause |
| Refusal, permissions, billing or policy failure | Handle the cause explicitly; do not switch models to bypass a restriction |

Follow the provider's [rate-limit guidance](https://developers.openai.com/api/docs/guides/rate-limits). Disable SDK retries when the application owns retries, or account for both layers so nested loops do not multiply attempts. If a retry delay exceeds the job's remaining deadline, defer the item. After the limit, expose failure or pending review and [alert the operator](/ai-service-alerts).

## Validate before saving

Check completion status and refusals before consuming a result, then validate required fields, types, allowed values and task-specific evidence. [Structured Outputs can still contain mistakes](https://developers.openai.com/api/docs/guides/structured-outputs). Schema compliance does not establish that a claim is supported.

For Northwind, a heat-retention claim needs supporting product evidence. Without it, reject the candidate or send it for review. Define when empty output legitimately means "nothing found" and when it means the task failed.

Keep generation retries separate from business writes. Save only an accepted result, using an idempotent operation keyed to the item and job so a replay does not publish it twice. Preserve the existing value when generation fails.

## When is fallback appropriate?

An explicit fallback can improve availability when its trade-offs are acceptable. Evaluate the replacement on the same cases, approve its quality threshold and data boundary, and define which failures may trigger it. Make its use visible to operators, record model provenance and provide a way to review or reprocess affected items.

Before release, force a timeout, a throttled response, an invalid output and an unexpected route change in a safe fixture. Confirm that attempts stay within the budget, unapproved models cannot produce a saved result, rejected output leaves stored data unchanged, and the operator can find the affected item. A green job is useful only when it also meets these conditions.
