An AI coding plan can look convincing while misunderstanding the requirements or relying on features that do not exist. Before a non-trivial change, **create and review a plan** with AI. Use the Discuss step in the [AI-assisted development workflow](/ai-assisted-development-workflow) to check its assumptions, scope and approach before implementation.

<endIntro />

## Why plan review matters

Reviewing a plan costs less time and fewer tokens than reworking an implementation. Look for:

* **Wrong assumptions** - Check the AI's understanding of requirements and architecture
* **Scope creep** - Remove changes the task does not need
* **Better alternatives** - Apply domain knowledge the AI may lack
* **Unresolved feedback** - Check that revisions address your concerns before approval

## Verify scope-changing premises before estimating

Before estimating or approving a plan, check assumptions that would materially change the work if wrong. For example, does the table, reusable service or API the plan relies on exist?

* **Find primary evidence** - Read definitions, callers, migrations and configuration at the relevant source revision. A matching class name is not enough
* **Check the relevant system** - If code cannot settle the claim, use authorised read-only checks such as schema queries or sanitised logs. Record the environment and check date
* **Revise the plan** - Mark each premise **verified**, **refuted** or **unverified**, link the evidence, and update the tasks and estimate

No search matches means **unverified**, not absent: the capability may have another name or live in another service.

In a synthetic Northwind example, an AI plan proposes adding a freight-surcharge row. The schema and calculation at the checked revision show no surcharge lookup. The plan therefore needs storage and calculation work as well as data entry. The surcharge policy still needs its owner's decision.

Keep the evidence and remaining unknowns with the PBI. Use a [time-boxed spike](/encourage-spikes-when-a-story-is-inestimable) when a technical unknown prevents a useful estimate; refer business-policy questions to the Product Owner.

## The traditional approach

Review the plan in your agent's chat, or open `PLAN.md` in your editor to read and edit it directly.

### Terminal - Discuss the plan

Quote the relevant section in chat and explain what should change.

### Editor - Review the whole plan

Open `PLAN.md` alongside the chat to review the whole plan rather than relying on the agent's summary.

* **Edit manually** - Revise the plan directly in the markdown file, then ask the AI to implement from the updated version
* **Cursor** - Built-in plan mode shows the plan inline; you can chat about specific sections directly without leaving the editor

### Limitations

These methods work, but they have clear drawbacks:

* Hard to give targeted feedback on specific sections without copying and pasting chunks of text
* No structured way to annotate, comment on, or reject parts of the plan
* Difficult to track what changed between plan iterations
* Suitable for small plans only - larger plans become unwieldy

## Tools that enhance plan review

A number of tools have popped up that give you a proper visual interface for reviewing and annotating AI plans, similar to how you would review a pull request on GitHub.

### Plannotator (Recommended)

[Plannotator](https://plannotator.ai/) provides a browser-based pull-request-style review UI - think GitHub PR review, but for AI plans. It makes structured, multi-round plan review practical for any plan size.

Key features:

* **Inline comments** on specific lines or sections (like GitHub PR review)
* **Delete** unwanted sections
* **Replace** or insert content
* **Global comments** for overall feedback
* **Multi-round iteration** - Deny with annotations → AI refines → re-review → approve
* **Works with any AI agent** - Claude Code, Codex, Copilot CLI, etc.
* Once approved, the AI builds based on the agreed, refined plan

### UltraPlan

[UltraPlan](https://code.claude.com/docs/en/ultraplan) bridges your local Claude Code CLI with Claude Code on the web. You kick off a planning task from your terminal, and it drafts the plan in the cloud while your terminal stays free. Once ready, you review, comment on, and revise the plan in a rich browser-based UI.

Key features:

* **Inline comments** - Highlight any passage in the plan and leave a comment
* **Emoji reactions** - React to sections to signal approval or concern
* **Outline sidebar** - Navigate between plan sections easily
* **Terminal stays free** - The plan drafts remotely so you can keep working
* **Flexible execution** - Approve to run on the web (auto-PR) or send the plan back to your terminal
* Launch via `/ultraplan` command, the keyword "ultraplan" in a prompt, or by promoting a local plan

### Claude Code VSCode Extension

The [Claude Code VSCode extension](https://marketplace.visualstudio.com/items?itemName=anthropic.claude-code) has built-in plan review features. When Claude generates a plan in VS Code, it automatically opens as a full markdown document in an editor tab - not just a chat message.

Key features:

* **Full document view** - The plan opens in a dedicated editor tab for easy reading
* **Inline comments** - Add comments directly on specific sections of the plan to give Claude targeted feedback
* **Approval workflow** - Once reviewed, choose to execute in auto mode, review each edit manually, or keep planning with feedback

<boxEmbed
  style="info"

    **Limitation:** Inline comments are freeform text feedback to Claude - there is no tracked resolution workflow like a GitHub PR review.

### GitHub Copilot

GitHub Copilot lets you review a plan before any code is written, in VS Code and on GitHub.com:

* **VS Code** - The [Plan agent](https://code.visualstudio.com/docs/agents/run/planning) opens the full plan in the editor, where you can edit it or add inline comments before you approve implementation
* **GitHub.com** - [Ask Copilot cloud agent to propose a plan](https://docs.github.com/en/copilot/how-tos/copilot-on-github/use-copilot-agents/research-plan-iterate), iterate on it in the session, then have it implement on a branch and create a pull request
