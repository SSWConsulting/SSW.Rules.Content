Before any app goes into Azure, someone has to set up the basics: the subscriptions, the network, who gets access and which policies apply. Microsoft calls this setup a landing zone. Many teams skip it and set up Azure by hand for each project, so every project ends up different and harder to secure.

That's why you should **design the landing zone first, following Microsoft's best practices**.

## Start from Microsoft's design instead of a blank page

1. **Start with an accelerator** - Microsoft's ready-made templates, called [accelerators](https://learn.microsoft.com/en-us/azure/cloud-adoption-framework/ready/landing-zone/implementation-options), deploy the recommended design as code. For most organizations they are "the fastest path"
2. **Decide every design area first** - Microsoft lists [eight](https://learn.microsoft.com/en-us/azure/cloud-adoption-framework/ready/landing-zone/design-areas) (e.g. identity, network, governance and automation)
3. **Separate environments with subscriptions** - Development, test and production each get their own, organized under management groups
4. **Set the rules with Azure Policy** - Assign [policies](/use-azure-policies) (e.g. allowed regions and required tags) to a management group. Every subscription below inherits them
5. **Give roles to groups, not to people** - Assign them on the subscription or resource group, a level below the policies
6. **Share only what many projects need** - Set those services up once, centrally (e.g. the network hub, DNS and one Log Analytics workspace)

## Know the rules before you build on one

When the landing zone already exists, ask the team that owns it what was decided, before you design your app. You can see the policies yourself in the Azure portal, under **Policy**, then **Assignments**:
