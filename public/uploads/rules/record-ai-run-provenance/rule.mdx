A saved AI product description contains a mistake. Since it was generated, the model, prompt and source rows have changed. The text alone cannot tell a developer which combination produced it, or which other descriptions need checking.

Whenever you keep an AI output, keep a linked provenance record: the evidence of how it was produced. Apply this to reports, generated code, classifications and summaries stored in a database, as well as published content.

<endIntro />

## Link the record to the output revision

Give each run an ID and link the saved output's exact revision to it. Store the provenance with the output, or in a durable record it references. Generate these fields in application code from the request, response and execution context; do not ask the model to describe its own provenance.

[Instrumenting AI calls](/use-opentelemetry) helps diagnose operations, and [monitoring cost and usage](/monitor-ai-cost-and-usage) helps control spend. This record answers a different question: **How was this particular saved result produced?** Keep it available for the result's retention period, even when operational traces are sampled or expire. A trace ID can be an extra link; it is insufficient if the trace is no longer available.

The [W3C PROV data model](https://www.w3.org/TR/prov-dm/) describes entities, the activities that produce them and the people or software responsible. For an AI feature, these correspond to the inputs and output, the run, and its initiator.

## Capture the conditions that affect the result

* **Model** - Provider, requested model ID and actual model/version returned, when exposed. Record an unavailable version as unknown; an alias is not evidence of a fixed version.
* **Instructions and implementation** - Immutable prompt/template version, its variables or protected input reference, and application release. Retain the referenced template, including system instructions and output schema.
* **Parameters** - The settings actually sent, such as temperature, output limit and seed where supported. Distinguish explicit values from provider defaults.
* **Inputs** - A retained snapshot or versioned row/document identifiers that resolve to what the run saw. A current row ID or live URL alone cannot recover an earlier value; a hash can check content but cannot restore it.
* **Tools and retrieval** - Ordered tool calls with version, arguments, outcomes and result references; retrieved document/chunk IDs and versions. Record none when unused. Reference protected payloads instead of copying sensitive content into logs.
* **Run and trigger** - Run ID, UTC start/end times and the authenticated user, service or job that initiated it. For several model calls, retain each call's conditions and identify the call or combination that produced the saved output.

[OpenTelemetry's GenAI conventions](https://github.com/open-telemetry/semantic-conventions-genai/tree/main/docs/gen-ai) define fields for inference, tool execution and retrieval. They are under development: use the conventions supported by your instrumentation and version your own stored record. The following YAML is an application example, not an OpenTelemetry or PROV interchange format.

Here, the application supplies rows directly from the retained snapshot, so there are no tool calls or retrieval steps. The versioned prompt and snapshot resolve to retained content. A maintainer can now find other outputs from prompt v7 and inspect the original inputs before deciding what to regenerate.

## Preserve the evidence without collecting everything

1. **Save the link reliably.** For a database output, commit its revision and provenance together in one transaction. For a file, retain a sidecar or manifest bound to that file revision, for example by its digest. Keep the previous revision's provenance when replacing an output.
2. **Protect and retain deliberately.** Restrict access to inputs, prompts and tool payloads; keep secrets out. Set retention and deletion rules for the output and its evidence together. If source content must be deleted earlier, record that limitation rather than claiming the run can still be reconstructed. [OpenTelemetry's content-capture guidance](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-spans.md#capturing-instructions-inputs-and-outputs) treats model content as sensitive and supports references to separate storage.
3. **Check the trail works.** Pick a saved output revision and resolve its run, prompt version and original inputs without consulting today's configuration. Query for other outputs from that prompt or model version. After a model change, use [evals](/run-evals-on-ai-features) to compare quality; provenance supplies the conditions, not a guarantee of identical text or a correct answer.

For media distributed outside your application, consider [C2PA Content Credentials](https://spec.c2pa.org/specifications/specifications/2.2/explainer/Explainer.html) to carry signed, tamper-evident provenance. A plain metadata record does not provide that protection, and even signed provenance does not prove the content is true.

For AI-assisted code changes, keep [the reasons for development decisions](/keep-the-why-from-ai-assisted-development) in the PR or ADR as well. Run metadata explains how an output was generated; the decision record explains why the change was wanted.
