A raw MDX diff shows what changed, not how the page will look. MDX components do not appear in the diff, and neither do the site's typography or spacing. Asking a reviewer to clone the repo and run the site locally is a lot of work for a content change they just need to read. Sending screenshots of a local render back and forth has the same problem. That is more work when the reviewer is not at a dev machine.

<endIntro />

## How to review a content change on a branch

In your [Git-based CMS](/git-based-cms-solutions), start from `main` and create or edit the content. Save it to a new branch with the editorial workflow. In [TinaCMS](https://tina.io), the [editorial workflow](https://tina.io/docs/drafts/editorial-workflow) creates a branch with a `tina/` prefix, and a draft pull request. After that prefix, follow your team's [branch naming convention](/branch-naming).

Then send the reviewer two links:

* The visual editor link for that branch. Test the link first, and name the branch in the message. The link may not select the branch on its own
* The pull request, so they can see the commits and approve or merge

Tina leaves a placeholder pull request description. Update it with the context the reviewer needs. See [Do you know how to write a great Pull Request (PR)?](/write-a-good-pull-request).

The reviewer reads the rendered page and makes small fixes in the editor. Each save commits to the branch, so there is no extra local render and no round of screenshots. When the review is done, merge the pull request. That is the publish step.

This works from a phone or an iPad. The visual editor is a link, so the reviewer does not need to clone the repo or run the site.
