A cloud-native app can leave you juggling APIs, databases, caches, and a growing pile of connection strings. Getting a fresh clone running becomes a hunt for the right ports, secrets, and startup order.

.NET Aspire brings local orchestration and integrations together so you can focus on the app instead of wiring services by hand. Its AppHost project is the local orchestrator that wires resources.

<endIntro />

## Make AppHost the local configuration entry point

* **Wire only the dependencies each service needs.** Northwind Web references the API; only the API receives the database connection and Orders service key. Configure the web HTTP client for service discovery too.
* **Pass configuration explicitly.** AppHost settings are not automatically copied to child processes. Commit dependency wiring and non-sensitive defaults; keep service-owned settings with the service and configure production separately.
* **Keep secrets out of source control.** Use an approved provider. Local User Secrets are unencrypted development storage; marking a parameter as secret does not encrypt its source.

See [Aspire external parameters](https://aspire.dev/fundamentals/external-parameters/) and [environment-variable injection](https://aspire.dev/fundamentals/environment-variables/) for configuration details.

### Check onboarding from a fresh clone

1. Obtain authorised development values.
2. Run a configuration check before starting resources. For scripted onboarding, report all missing input names without their values and exit non-zero if any are missing.
3. Start AppHost and confirm web-to-API and API-to-dependency access without per-service edits. Having a value does not prove the credentials work.

Document any extra configuration needed to launch a service outside AppHost.

## Example - Adding Redis Cache to a .NET app

### Manual setup - with Docker Compose

Set up a Redis container (e.g., using Docker Compose).

```yaml
services:
  redis:
    image: redis:latest
    container_name: redis-cache
    ports:
      - "6379:6379"
    command: ["redis-server", "--requirepass", "examplepassword"] # Local example only
    volumes:
      - redis_data:/data # Persist data locally

volumes:
  redis_data:
    driver: local
```

Write custom code to handle connection strings and inject them into your application (this needs to be manually kept in sync with all your environments).

```csharp
var redisConnection = Environment.GetEnvironmentVariable("REDIS_CONNECTION_STRING")
    ?? throw new InvalidOperationException("REDIS_CONNECTION_STRING is required.");
services.AddStackExchangeRedisCache(options =>
{
    options.Configuration = redisConnection;
    options.InstanceName = "Northwind";
});
```

**Figure: Bad example - Redis setup and application configuration must be kept in sync manually**

Docker Compose remains a valid choice. Aspire removes this example's manual connection wiring; it does not remove the need to configure each environment.

### Simplified setup - with .NET Aspire

Aspire handles Redis setup and connection string injection for you:

In AppHost, configure the Redis resource and reference it from the API:

```csharp
var builder = DistributedApplication.CreateBuilder(args);
var cache = builder.AddRedis("cache");
builder.AddProject<Projects.NorthwindApi>("api")
      .WithReference(cache)
      .WaitFor(cache);

builder.Build().Run();
```

In the API project, install `Aspire.StackExchange.Redis.DistributedCaching` and register `IDistributedCache` using the same resource name:

```csharp
var builder = WebApplication.CreateBuilder(args);
builder.AddRedisDistributedCache("cache");
```

**Figure: Good example - AppHost supplies the connection for the named Redis resource**

The API still uses `IDistributedCache`, while AppHost manages the local Redis container and supplies its connection string. See the [Redis distributed caching integration](https://aspire.dev/integrations/caching/redis-distributed/) for package and setup details.
